## 1. 表是怎么被推导出来的（四步法）

不是凭经验拍的。有一套可以复述的推导过程，被追问「为什么这么设计」时按这个顺序讲：

**第一步：从题目原文抽名词。**
业务名词是「客户」「聊天记录」「客户状态」「AI 的判断结果」「企业配置」——五个名词，五个候选实体。

**第二步：检查每个实体的「写入者 / 写入频率 / 写入模式」。**
这一步决定拆还是合。三个维度组合不同，就必须分开：

| 实体 | 写入者 | 频率 | 模式 |
|---|---|---|---|
| 客户档案 | 销售 | 低频 | 修改 |
| 客户状态 | 代码（消费 AI 输出） | 高频 | **覆盖** |
| 聊天记录 | 人 | 中频 | **只追加** |
| AI 判断 | 代码 | 高频 | **只追加** |

**第三步：检查每个查询需求。**
要「一条 SQL 查出所有高意向客户」，阶段就必须是**列**，不能是 JSON blob。

**第四步：检查重复与并发风险。**
题目第三十节的现场实战题（消息重复、AI 重复回复、Follow-up 重复）全在问这一层——答案统一是**数据库唯一约束**，不是应用层 if 判断。

## 2. 总览：每张表的依据与作用

| 表 | 构建依据（题目映射） | 写入者 | 写入模式 | 核心作用 |
|---|---|---|---|---|

## 3. 关系形状

```text
Tenant ─┬─< Customer ─┬─< Message
        │             ├── CustomerState        (1:1)
        │             ├─< AgentRun             (每次判定一条)
        │             └─⚪ CustomerFact         (设计保留，不实现)
        │             └─⚪ ConversationSummary  (设计保留，不实现)
        ├─< Message
        ├─< CustomerState
        ├─< AgentRun
        ├─⚪ CustomerFact
        └─⚪ ConversationSummary
```

**`Customer` 是聚合根**，所有业务数据挂在它下面，而它挂在 `Tenant` 下面。这条链就是租户隔离的物理形状。

注意 `Message` / `AgentRun` 等表上**冗余了 `tenantId`**，虽然逻辑上可以从 Customer 推出来。冗余的目的是让每一次查询都能直接带租户条件，**不需要 join 才能确定归属**。

## 4. 完整 Prisma Schema

> 已按「确定使用 PostgreSQL」修正：`tags` 用原生数组、`config` / `output` 用 JSONB、`createdAt` 用 `timestamptz`。

```prisma
enum MessageRole {
  CUSTOMER
  SALES
  SYSTEM
}

// ───────────────── 租户 ─────────────────
model Tenant {
  id        String   @id @default(cuid())
  slug      String   @unique          // swimming / machinery
  name      String
  industry  String?
  salesGoal String                    // 自然语言销售目标
  tone      String?
  // rules[] / stageDefs{} / needHumanTriggers[] / factKeys[] / products[] / maxFollowUps
  config    Json     @db.JsonB
  createdAt DateTime @default(now()) @db.Timestamptz(3)
  updatedAt DateTime @updatedAt      @db.Timestamptz(3)

  customers Customer[]
  messages  Message[]
  states    CustomerState[]
  runs      AgentRun[]
  facts     CustomerFact[]
  summaries ConversationSummary[]

  @@map("tenants")
}

// ───────────────── 客户 ─────────────────
model Customer {
  id         String    @id @default(cuid())
  tenantId   String
  name       String
  channel    String    @default("manual")   // 预留 wechat / phone
  externalId String?                        // 渠道侧 ID
  tags       String[]  @default([])         // 原生数组
  archivedAt DateTime? @db.Timestamptz(3)   // 软删除
  createdAt  DateTime  @default(now()) @db.Timestamptz(3)
  updatedAt  DateTime  @updatedAt     @db.Timestamptz(3)

  tenant    Tenant                @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  messages  Message[]
  state     CustomerState?
  runs      AgentRun[]
  facts     CustomerFact[]
  summaries ConversationSummary[]

  @@unique([tenantId, externalId])            // 渠道去重（复合，含租户）
  @@index([tenantId, archivedAt, updatedAt])  // 客户列表页
  @@map("customers")
}

// ───────────────── 消息 ─────────────────
model Message {
  id          String      @id @default(cuid())
  tenantId    String                            // 冗余：隔离 + 免 join
  customerId  String
  role        MessageRole
  content     String
  turnId      String?                           // 连续消息聚合（进阶挑战 2）
  source      String      @default("manual")    // manual | ai_suggested | followup
  clientMsgId String?                           // 幂等：前端重发不产生重复
  createdAt   DateTime    @default(now()) @db.Timestamptz(3)

  tenant   Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  customer Customer @relation(fields: [customerId], references: [id], onDelete: Cascade)

  @@unique([customerId, clientMsgId])
  @@index([tenantId, customerId, createdAt])    // 会话页拉最近 N 条
  @@index([customerId, turnId])
  @@map("messages")
}

// ───────────────── 客户状态（1:1） ─────────────────
model CustomerState {
  customerId String @id                          // 主键即外键，强制 1:1
  tenantId   String

  leadStage       String  @default("NEW")
  intent          String?
  needHuman       Boolean @default(false)
  humanReason     String?
  humanResolvedAt DateTime? @db.Timestamptz(3)   // 销售手动解除人工

  followUpCount  Int       @default(0)
  lastFollowUpAt DateTime? @db.Timestamptz(3)

  lastCustomerMessageAt DateTime? @db.Timestamptz(3)
  lastSalesMessageAt    DateTime? @db.Timestamptz(3)
  lastActivityAt        DateTime? @db.Timestamptz(3)  // 派生：max(上两者)，为跟进扫描
  lastAnalysisAt        DateTime? @db.Timestamptz(3)

  version   Int      @default(0)                 // 乐观锁 + 变更计数
  updatedAt DateTime @updatedAt @db.Timestamptz(3)

  tenant   Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  customer Customer @relation(fields: [customerId], references: [id], onDelete: Cascade)

  @@index([tenantId, leadStage, needHuman])
  @@index([tenantId, lastActivityAt])            // 跟进任务扫描
  @@map("customer_states")
}

// ───────────────── AI 判定审计 ─────────────────
model AgentRun {
  id               String  @id @default(cuid())
  tenantId         String
  customerId       String
  trigger          String  @default("CUSTOMER_MESSAGE")  // CUSTOMER_MESSAGE | FOLLOW_UP
  triggerMessageId String?                                // 跟进触发时为 null

  status    String   // SUCCESS | REPAIRED | FALLBACK | FAILED
  model     String
  latencyMs Int
  attempt   Int      @default(1)

  inputDigest     Json    @db.JsonB   // 发给模型的上下文快照
  rawOutput       String?             // 模型原始返回，排障用
  output          Json?   @db.JsonB   // 校验后的结构化结果
  rulesHit        String[] @default([])
  guardrailIssues String[] @default([])
  error           String?

  // 采纳情况 → 形成反馈闭环
  suggestionSent   Boolean @default(false)
  suggestionEdited Boolean @default(false)

  createdAt DateTime @default(now()) @db.Timestamptz(3)

  tenant   Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  customer Customer @relation(fields: [customerId], references: [id], onDelete: Cascade)

  @@unique([customerId, triggerMessageId])   // 幂等：一条消息只判定一次（NULL 之间互不冲突）
  @@index([tenantId, customerId, createdAt])
  @@index([tenantId, trigger, status])       // 按链路看成功 / fallback / 失败率
  @@map("agent_runs")
}

// ───────────────── 客户档案（长期事实） ─────────────────
// ⚪ 24H 内不实现。保留在此仅用于说明长对话场景的设计方案。
model CustomerFact {
  id         String @id @default(cuid())
  tenantId   String
  customerId String

  category        String   // IDENTITY | NEED | CONSTRAINT | OBJECTION
  key             String   // 受控词表：child_age / budget / concern
  value           String
  evidence        String   // 客户原话，入库前校验是真实消息子串
  sourceMessageId String?
  confidence      Float    @default(0.8)
  status          String   @default("ACTIVE")  // ACTIVE | SUPERSEDED | REJECTED
  validFrom       DateTime @default(now()) @db.Timestamptz(3)
  expiresAt       DateTime? @db.Timestamptz(3)

  tenant   Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  customer Customer @relation(fields: [customerId], references: [id], onDelete: Cascade)

  @@index([tenantId, customerId, key, status])
  @@map("customer_facts")
}

// ───────────────── 中期摘要 ─────────────────
// ⚪ 24H 内不实现。同上。
model ConversationSummary {
  id         String   @id @default(cuid())
  tenantId   String
  customerId String
  fromAt     DateTime @db.Timestamptz(3)
  toAt       DateTime @db.Timestamptz(3)
  content    String
  msgCount   Int
  createdAt  DateTime @default(now()) @db.Timestamptz(3)

  tenant   Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  customer Customer @relation(fields: [customerId], references: [id], onDelete: Cascade)

  @@index([tenantId, customerId, toAt])
  @@map("conversation_summaries")
}
```

### 为什么最终选 PostgreSQL（非部署因素）

排除掉"京东云常驻主机"这个部署前提后，仍然有四条硬理由：

| # | 理由 | 本题中的具体用处 |
|---|---|---|
| 1 | **跨表事务的原子性** | 一次判定要原子写 `Message` + `AgentRun` + `CustomerState`，否则出现"审计日志与状态不一致"的幽灵判断 |
| 2 | **完整的类型能力** | Prisma 的 SQLite provider **不支持 `Json` 和 `enum`**，会被迫降级成 String + 到处 `JSON.parse`，类型安全从数据库一路漏到业务代码 |
| 3 | **分析与扩展能力** | 后续做漏斗转化率（窗口函数 / CTE）、检索历史成交案例（pgvector）、阶段停留时长（物化视图） |
| 4 | **不锁死自己** | 京东云有 RDS PostgreSQL，量大了改一行 `DATABASE_URL` 就切托管，schema 不用动 |

补充一条实际压力：`AgentRun` 是只追加表，行数增长是消息数的 1~2 倍。SQLite 的单写者模型在这里会成为真实瓶颈。

## 5. 逐表说明

### 5.1 Tenant —— 多租户的隔离根

**依据**：核心任务 5 要求「至少支持两个不同的 Tenant / 企业配置」，且必须证明「切换 Tenant 后，AI 的判断或回复确实受到对应销售规则影响」。这需要一个实体承载「销售目标 + 规则 + 阶段定义」。

**作用**：两个身份。

```text
① 隔离的根节点 —— 所有业务表挂在它下面，租户边界就是这棵树的分支
② 配置注入源   —— AI pipeline 每次组装 prompt 时从这里读规则
```

**关键决策：`config` 用 JSONB，不拆 `TenantRule` 表。**

依据是**当前的查询模式**：规则只需整体读出来注入 prompt，不需要按条件筛选。

**但这是明确的技术债，要主动说**：将来必然要拆，因为运营会问「R1 这条规则的命中率是多少」——而这个问题现在的答案埋在 `AgentRun.rulesHit` 数组里，查起来很难看。

> **JSON 适合存「整体读取」的东西，不适合存「需要统计」的东西。**

### 5.2 Customer —— 聚合根

**依据**：核心任务 1 要求「创建客户、查看客户列表、进入客户详情」。客户是所有业务数据的挂载点。

**作用**：定义归属边界。消息、状态、判定、事实全挂在它下面，删客户要能级联清干净。

**关键决策：`@@unique([tenantId, externalId])` 是复合唯一键。**
同一个外部 ID 在不同租户下是两个不同的客户。如果只对 `externalId` 做唯一，租户 A 的客户会和租户 B 的撞车。

> **隔离边界必须体现在约束里，不只是体现在查询里。**

### 5.3 Message —— 事实来源

**依据**：核心任务 1 规定了四个必存字段（内容、发送方、时间、所属客户）和「刷新页面后聊天记录不能消失」；核心任务 4 要求「最终发送内容必须进入聊天记录，并且参与下一轮 AI 判断」。

**作用**：系统里**唯一的 append-only 事实来源**。所有 AI 判断的输入从这里来，所有「客户到底说了什么」的争议以它为准。

**为什么强调 append-only**：聊天记录是历史事实，永远不该被 UPDATE。这一个性质带来三个好处：

```text
① 天然免疫并发覆盖（没有 lost update）
② 可以无限回放
③ 备份与归档策略简单
```

> **如果消息可以被改写，「审计」这个词就没有意义了。**

**字段依据**：

| 字段 | 依据 |
|---|---|
| `tenantId` 冗余 | 隔离查询不需要 join 回 Customer 才能确定归属 |
| `clientMsgId` | 现场实战题「消息重复处理」的答案，唯一约束在数据库层兜底 |
| `turnId` | 进阶挑战 2 的预留，连续消息聚合成一轮 |
| `source` | 区分人工发的 / AI 建议采纳的 / 跟进自动生成的，Demo 时能展示「这条是 AI 建议的」 |
| `role` 用数据库 enum | 三个值固定不变，数据库级校验比应用层可靠 |

### 5.4 CustomerState —— 唯一可变的业务状态

**依据**：核心任务 3 的原话是「这个项目不能只是：消息 → 调用 LLM → 回复」，并给出明确流程「新消息 → 读取旧状态 → AI 判断 → 产生建议 → 更新状态」。

> **「读取旧状态」和「更新状态」这两个动作，就是这张表存在的全部理由。**

**作用**：系统里唯一一张会被反复覆盖的业务表，有三重身份：

```text
① AI pipeline 的输入   → 读出来序列化进 prompt
② UI 的渲染数据源      → 客户列表的徽标、红旗、排序
③ 销售的可编辑对象     → 人工可以修正状态、解除转人工
```

**这三重身份是它必须放在自己的数据库里、而不能藏在框架内部状态里的原因——它同时被机器和人读写。**

**为什么 1:1 独立成表而不是并进 Customer**：

| 原因 | 说明 |
|---|---|
| 读写频率不同 | 状态每轮改，客户档案几乎不改 |
| 生命周期不同 | 状态易变，档案稳定 |
| 需要独立审计 | `version` 做变更计数与乐观锁 |

**为什么主键就是 `customerId`**：用主键即外键的方式，在**数据库层**强制 1:1。应用层忘写检查也不会出现两个状态行。

**字段来源分两类——这个划分决定了一个字段该不该在这张表里**：

| 类型 | 字段 | 来源 |
|---|---|---|
| **判断型** | `leadStage` / `intent` / `needHuman` | 模型提出 → **代码护栏裁决** |
| **事实型** | 各种时间戳 / `version` / `followUpCount` | **代码观察** |

**事实型字段模型没有资格写**——它连消息是几点发来的都不知道。

**一个必须明确的业务规则：`needHuman` 用 OR（棘轮），不用覆盖。**

```ts
needHuman: prev.needHuman || analysis.need_human
```

AI 一旦判定要转人工，下一轮它说 false 也撤销不了。**谁能解除人工状态？** 只有销售在 UI 上手动点「已处理」（写 `humanResolvedAt`）。

如果写成覆盖式，模型就有权把一个已经交给人的客户悄悄收回去——这在业务上是错的。

### 5.5 AgentRun —— AI 决策的黑匣子

**这张表不是题目要求的，是主动加的。** 依据是四条要求的共同前提——**LLM 调用不可复现，除非你把每次调用记录下来**：

```text
· 核心任务 2 要求输出 reason（要能解释为什么这么判断）
· 进阶挑战 3 要求 AI 异常不能崩溃（要能定位失败原因）
· 答辩会问「AI 为什么判成 HIGH_INTENT」「系统最脆弱的地方在哪」
· 现场实战题会问「接口突然报错怎么办」
```

**它的五个作用**：

| # | 作用 | 对应字段 |
|---|---|---|
| ① | 审计每次判定的完整输入输出 | `inputDigest` / `output` |
| ② | 排障：是超时、格式错还是字段缺失 | `rawOutput` / `error` / `status` |
| ③ | 幂等：一条消息只判定一次 | `@@unique([customerId, triggerMessageId])` |
| ④ | 指标：fallback 率 | `status` 分布 |
| ⑤ | **反馈闭环** | `suggestionSent` / `suggestionEdited` |

**第 ⑤ 项现在没用上，但它是从「策略」走向「闭环」的接口。** 有了它才能回答「我上次建议的回复，销售改了没有」，把这个结果喂回下一轮上下文，模型才第一次能看见自己建议的后果。

> 这张表体现的是主动设计：不是把题目要求翻译成代码，而是识别出「可解释性」是评分点，然后为它准备数据结构。

#### `trigger` 字段：同一张表承载两条链路

主链路和 Follow-up 复用同一个 `analyze()` 入口（决策 Q12），产生的判定结果结构完全相同，所以共用一张表，用一个字段区分：

```text
trigger = CUSTOMER_MESSAGE   客户发了消息 → 回应
trigger = FOLLOW_UP          定时器发现客户静默 → 主动开口
```

好处是可以分开看两条链路的质量：

```sql
SELECT trigger, status, COUNT(*)
FROM agent_runs WHERE tenant_id = $1
GROUP BY trigger, status;
```

**如果跟进的 fallback 率明显高于主链路，说明跟进场景的 prompt 需要单独调。** 没有这个字段，这个问题就看不见。

#### 两条链路的幂等机制不一样

这是个容易漏掉的点：

| 链路 | 幂等键 | 机制 |
|---|---|---|
| 客户消息 | `(customerId, triggerMessageId)` 唯一约束 | 同一条消息重复触发时插入冲突，直接返回已有结果 |
| Follow-up | **没有消息 ID 可用** | 靠 `followUpCount` 的**比较并交换（CAS）** |

跟进按时间触发，没有 `triggerMessageId` 当幂等键，所以防重放在状态更新上：

```ts
// 只有 count 没被别的执行者抢先改过，才轮到本进程处理
const claimed = await tx.customerState.updateMany({
  where: { customerId, followUpCount: prev.followUpCount },   // ← 乐观锁
  data: {
    followUpCount: { increment: 1 },
    lastFollowUpAt: new Date(),
    // 注意：这里没有 leadStage / intent —— 见决策 Q13
  },
})
if (claimed.count === 0) return   // 别人先处理了，本次放弃
```

**这就是为什么「触发机制的选择决定了幂等要在哪里做」**：定时器重复注册、按钮被连点、扫描并发执行，是三种不同的重复来源，而 `(customerId, triggerMessageId)` 这条唯一约束对它们一个都拦不住。

> 注意上面那段事务里**只更新了两个跟进字段，没有 `leadStage` 和 `intent`**。这是决策 Q13 落到代码里的样子：跟进是我们主动说话，客户没提供新信息，所以不驱动状态迁移。

### 5.6 ⚪ CustomerFact / ConversationSummary —— 长对话的答案（**不实现**）

**先说清楚**：这两张表**不进 migration、不写代码**。它们是决策记录第 4 节放弃清单里的一条，写在这里的用途只有一个——**回答「长对话怎么办」这类追问时，能讲出一套完整的方案而不是"没做"**。

**依据**：不属于题目要求，是从「进 prompt 的内容不能随对话长度线性增长」这个约束推导出来的。

**作用**：把「记忆」拆成三层，各用不同结构承载：

```text
CustomerFact        事实层  不随对话增长   → 持久化注入
ConversationSummary 叙事层  缓慢增长       → 持久化注入
Message             原文层  固定窗口       → 最近 N 条
```

三层合计约 1600 token，**与对话长度无关**；而 500 条原文是 25000–50000 token。

**`CustomerFact` 里最关键的是 `evidence` + `sourceMessageId`**：

> 每条事实必须能指回客户的原话，入库前用**子串校验**，校验不过就整条丢弃。

这是防止「模型幻觉被固化成事实」的**结构性**防线。

```ts
function validateFact(fact, messages) {
  return messages.some(m => m.content.includes(fact.evidence))
    ? { ok: true }
    : { ok: false, reason: 'evidence_not_grounded' }
}
```

**靠结构，不靠 prompt 里写「请不要编造」。**

**事实会变，所以用「失效」而不是「覆盖」**：同 key 出现新值时，把旧的置为 `SUPERSEDED`，新建一条 `ACTIVE`。只有 ACTIVE 的进 prompt。

> 不覆盖，留版本——和状态迁移是同一个思路。

## 6. 索引设计

**每个索引都要能指回一条真实查询。** 这是设计表时最容易被追问的地方。

| 查询 | 用到的索引 |
|---|---|
| 客户列表：`tenantId` + 按更新时间倒序 | `customers(tenantId, archivedAt, updatedAt)` |
| 会话页拉最近 20 条消息 | `messages(tenantId, customerId, createdAt)` |
| 跟进扫描：非终态、非人工、超时未动 | `customer_states(tenantId, lastActivityAt)` |
| 幂等检查：这条消息判定过没有 | `agent_runs(customerId, triggerMessageId)` 唯一约束 |
| 分链路观察 AI 失败率 | `agent_runs(tenantId, trigger, status)` |
| ⚪ 拼装档案（不实现） | `customer_facts(tenantId, customerId, key, status)` |
| ⚪ 连续消息（不实现） | `messages(customerId, turnId)` |

**实际会创建的索引就是上表前五行对应的那几条。** 后两行是设计保留，字段在 schema 里留着但当前代码不查——**留字段不留查询，是为了将来加功能时不用做 migration。**

### `lastActivityAt` 是刻意的反规范化

它等于 `max(lastSalesMessageAt, lastCustomerMessageAt)`，本来可以算出来。但存成真列之后：

```text
跟进扫描：从一个「带 OR 的复杂条件」变成「干净的索引范围扫描」
代价：多维护一个字段
收益：热路径查询变简单
```

**这类取舍讲出来，比背索引名有价值得多。**

### 部分索引（PostgreSQL 特性）

这是 PG 相对其他关系库的一个具体优势。举例：如果将来实现了事实表，只需要索引 ACTIVE 的行——

```sql
CREATE INDEX idx_facts_active
  ON customer_facts (tenant_id, customer_id, key)
  WHERE status = 'ACTIVE';
```

**24H 内用不到**（事实表不实现），但这个能力是选 PG 的理由之一：**条件索引、GIN 索引这类东西在需要的时候不用换库。**

## 7. 字段约定

### 7.1 主键：为什么用 cuid 而不是自增整数

| 理由 | 说明 |
|---|---|
| 不泄漏业务量 | 竞对能通过自增 ID 的增长估算你的单量 |
| 跨环境迁移不冲突 | 开发库和线上库合并时自增会撞 |
| 降低 IDOR 攻击面 | ID 出现在 URL 里，自增让「改个数字试试别人客户」毫无成本 |

cuid 不能替代授权检查，但**白送的攻击面没必要留着**。

### 7.2 时间：统一 `timestamptz`，存 UTC

销售系统里到处是时间判断——多久没联系、是否超过跟进窗口、按最后活动排序。

```text
数据库存 UTC → 展示时转本地时区
绝不要存本地时间字符串
```

### 7.3 enum 还是 String

| 字段 | 类型 | 理由 |
|---|---|---|
| `Message.role` | **enum** | 三种值固定不变，数据库级校验最可靠 |
| `leadStage` / `intent` | **String** | **租户可配置**。乐蒙和机械之家的阶段语义不同，未来可能新增。用 enum 意味着每加一个值都要 migration，删值还删不掉 |

规则：**固定的用 enum，可配置的用 String + 应用层 Zod 校验。**

### 7.4 列还是 JSON

| 用途 | 选型 | 例子 |
|---|---|---|
| 需要查询 / 筛选 / 排序 / 统计 | **列** | `leadStage`、`lastActivityAt`、`status` |
| 只需要整体读写，或需要回放 | **JSONB** | `Tenant.config`、`AgentRun.output` |

> **可查询的字段用列，只用于回放的用 JSON。**

### 7.5 数组还是逗号字符串

确定用 PG 之后，`tags` / `rulesHit` / `guardrailIssues` 都用 `String[]`。

判断标准很简单：**只有当你要写 `WHERE 'R1' = ANY(rules_hit)` 这类查询时，数组才值得。** 如果只是展示和写日志，逗号字符串也够——但既然 PG 原生支持数组且类型更干净，没有理由退回字符串。

### 7.6 删除

| 对象 | 方式 |
|---|---|
| Tenant / Customer 删除 | 数据库 `onDelete: Cascade` 一路往下清 |
| 客户的"删除" | 用 `archivedAt` 软删除，保留数据可追溯 |

## 8. 数据不变量：谁保证什么

这个划分能说明是否理解分层边界。**判断标准是：数据库能廉价保证、且永远不该被违反的，就下沉到数据库；依赖上下文（租户身份、AI 输出、业务规则）的，只能在应用层做。**

| 保证方 | 保证什么 | 具体机制 |
|---|---|---|
| **数据库** | 外键存在 | `@relation` |
| | 非空 | 字段不加 `?` |
| | 唯一性 / 幂等 | `@@unique([customerId, clientMsgId])`、`@@unique([customerId, triggerMessageId])` |
| | 1:1 关系 | `CustomerState.customerId` 既是主键又是外键 |
| | 级联删除 | `onDelete: Cascade` |
| | 时间类型与顺序 | `timestamptz` |
| | 租户边界的复合唯一 | `@@unique([tenantId, externalId])` |
| **应用层** | 租户授权 | 这个人能不能碰这个 customerId |
| | 状态迁移合法性 | 单调性、终态锁 |
| | AI 输出校验 | Zod schema |
| | 事实证据校验 | `evidence` 子串匹配 |
| | 业务规则护栏 | `guardrails.ts` |

## 9. 常用查询速查

### 客户列表（带状态）

```ts
const customers = await prisma.customer.findMany({
  where: { tenantId, archivedAt: null },
  include: { state: true },
  orderBy: { updatedAt: 'desc' },
  take: 50,
})
```

### 会话页：拉最近 N 条并转成时间正序

```ts
const rows = await prisma.message.findMany({
  where: { tenantId, customerId },
  orderBy: { createdAt: 'desc' },
  take: 20,
})
const history = rows.reverse()   // ★ 别忘了 reverse
```

### 跟进任务扫描

```ts
const due = await prisma.customerState.findMany({
  where: {
    tenantId,
    leadStage: { notIn: ['WON', 'LOST'] },
    needHuman: false,
    followUpCount: { lt: 2 },
    lastActivityAt: { lt: new Date(Date.now() - 3 * 24 * 3600 * 1000) },
    // ★ 最后一条必须是 SALES 发的 —— 决策 Q7 的核心条件
    //   用两个时间戳的比较表达，不需要 join 回 messages 找最后一条
    lastSalesMessageAt: { not: null },
  },
  include: { customer: true },
  take: 20,
})
```

`lastSalesMessageAt > lastCustomerMessageAt` 这个条件，正是 `CustomerState` 上同时保留两个时间戳字段的理由——**如果只存一个 `lastActivityAt`，这个判断就必须 join 回 `Message` 表每次现算。**

### 幂等检查（判定是否已存在）

```ts
const existing = await prisma.agentRun.findUnique({
  where: { customerId_triggerMessageId: { customerId, triggerMessageId } },
})
if (existing) return existing.output   // 直接返回旧结果
```

### 拼装客户档案（进 prompt 用）

```ts
const facts = await prisma.customerFact.findMany({
  where: { tenantId, customerId, status: 'ACTIVE' },
  orderBy: { validFrom: 'asc' },
})
// 校验每条 evidence 是否是真实消息子串，不通过的丢弃
```

### 观察 AI 健康度

```ts
const runs = await prisma.agentRun.groupBy({
  by: ['trigger', 'status'],      // 分开看主链路和跟进链路
  where: { tenantId },
  _count: true,
  _avg: { latencyMs: true },
})
// FALLBACK / FAILED 占比 = 「系统最脆弱的地方」这个答辩题的答案
// 如果 FOLLOW_UP 的失败率明显高于 CUSTOMER_MESSAGE，说明跟进的 prompt 要单独调
```

### 事务写法（原子写多表）

```ts
// ★ AI 调用必须在事务之外
const analysis = await callLLM(...)          // 可能 15 秒

await prisma.$transaction(async (tx) => {
  await tx.agentRun.create({ ... })          // 审计
  await tx.customerState.upsert({ ... })     // 状态
  await tx.customerFact.createMany({ ... })  // 事实（可选）
})                                            // 事务只有几十毫秒
```

### 并发保护（需要时）

```sql
-- 同一客户并发判定时防止 lost update
SELECT * FROM customer_states WHERE "customerId" = $1 FOR UPDATE;
```

## 10. 已知技术债与演进路线

主动列出来，答辩时被问到能直接答。

| # | 技术债 | 现在的做法 | 什么时候必须改 | 怎么改 |
|---|---|---|---|---|
| 1 | `Tenant.config` 是 JSONB | 整体读取注入 prompt | 运营要统计「每条规则的命中率」 | 拆 `TenantRule` 表，带 `enabled` / `priority` / `version` |
| 2 | 规则硬校验写在代码里 | 关键字 / 正则判断 | 规则数量超过 5~10 条，或租户要自定义 | 抽象成带条件的规则引擎（条件表达式 + 动作） |
| 3 | `AgentRun` 无归档 | 每次判定一行，永久保留 | 表超过千万行 | 按 `createdAt` 分区 + 冷数据归档到对象存储 |
| 4 | 无分布式锁 | 靠唯一约束 + 事务 | 同一客户高并发写入 | Redis 锁，或 `SELECT FOR UPDATE` 显式加锁 |
| 5 | 连续消息未聚合 | `turnId` 字段已预留 | 接真实渠道 | Redis 滑动窗口缓冲，静默到期后合并为一轮 |
| 6 | 跟进靠轮询扫描 | 进程内定时器（60s）+ 手动触发 | 客户量过十万 | 延迟队列（BullMQ / pg-boss），每个客户一个 delay job |
| 7 | 单库单实例 | 京东云自建 Docker | 需要高可用 | 切京东云 RDS PostgreSQL，加只读副本 |
| 8 | 无 RLS | 应用层带 `tenantId` | 多团队协作、合规要求 | Postgres 行级安全策略做第二层兜底 |
| 9 | **长对话无记忆分层** | 固定取最近 20 条（`HISTORY_LIMIT`） | 客户历史超过 100 条 | 落地 `CustomerFact` + `ConversationSummary` 三层结构（见本文档 5.6） |
| 10 | **登录是单口令，无用户体系** | `middleware.ts` 比对哈希 | 需要多用户 / 审计谁改了什么 | 引入用户表 + 会话，`CustomerState` 的修改记录带上操作人 |

**演进顺序的核心逻辑**：**先保证核心链路正确，再解决量的问题。** 上表 1~3 是「功能变复杂」触发的，4~6 是「并发和规模」触发的，7~8 是「生产可靠性」触发的——三条线可以并行推进，但都不该在 24H 内做。

> 第 9、10 条是**主动承认的缺口**，属于 `决策记录.md` 第 4 节放弃清单的延伸。答「Known Issues」和「Next 3 Days」时直接用这两条。

## 11. 开发检查清单

写每一段数据库代码前对一遍：

```text
[ ] 查询的 where 里有 tenantId 吗？

[ ] seed 用了 upsert 吗？
```
