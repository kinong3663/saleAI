## 1. 一页速览

| 层 | 选择 | 一句话理由 |
|---|---|---|
| 前后端 | **Next.js 14+（App Router）+ TypeScript** | 一门语言覆盖页面和 API，只留一个部署目标 |
| 语言 | **TypeScript（strict）** | 结构契约从数据库到 UI 是同一条类型链 |
| ORM | **Prisma** | schema 即数据设计文档，且生成 TS 类型 |
| 数据库 | **PostgreSQL 16** | 跨表事务 + 类型能力（详见数据表文档） |
| LLM 接入 | **DeepSeek（OpenAI 兼容）+ 自写 provider 封装** | 国内直连稳定、成本极低、换模型只改环境变量 |
| 结构化输出 | **Zod + JSON Schema strict，失败降级 `json_object`** | 兼容接口不一定支持 strict，需运行时能力探测 |
| 后台任务 | **进程内 `setInterval` + 手动触发接口** | 常驻容器才可行，serverless 上活不过一次请求 |
| 访问控制 | **`middleware.ts` 单口令门锁** | 挡随机路人，非身份系统；按零摩擦清单实现 |
| 样式 | **Tailwind（最简用法）** | 题目明确不考 UI |
| 部署 | **京东云云主机 + Docker Compose** | 国内可直连，面试方能打开 |

> **本节的每一项都已通过质询确认**，理由与可逆成本见 `决策记录.md`。如果本文档与决策记录冲突，**以决策记录为准**。

**核心架构约束（开发时最重要的两条）**：

```text
① 只有 src/server/agent/ 知道 LLM 的存在，其他模块调的是普通函数
② 所有 service 函数以 tenantId 作为第一个参数
```

## 2. 选型判据

不按「哪个先进」选，按「哪条路径失败风险最小」选。五个判据：

| 判据 | 说明 |
|---|---|
| 工作量覆盖度 | 技术栈覆盖了题目多少工作量？剩下多少要用第二种语言兜？ |
| 交付风险 | 上线是硬性要求，这条路径上有几个必须做对的环节？ |
| 契约一致性 | 结构化输出的字段，从数据库到 UI 要经过几处类型定义？ |
| 可解释性 | 会不会让「AI 为什么这么判断」变模糊？ |
| 脚手架成本 | 框架本身要吃掉多少时间？ |

**关键判据是前两个。** 24H 硬约束下，任何「两套栈」的方案都会暴露风险。

### 这道题的工程量分布

| 任务 | 归属层 | Python 生态更优？ |
|---|---|---|
| 1 客户与聊天记录 CRUD | Web 后端 + DB | 打平 |
| 2 客户列表 / 详情 / 聊天界面 | 前端 | 无优势 |
| 3 AI 结构化判断 | LLM 调用（**一次**） | 略优 |
| 4 Customer State 读写 + 展示 | Web 后端 + 前端 | 打平 |
| 5 销售编辑 / 发送 / 落库 | 前端 + 后端 | 无优势 |
| 6 Tenant 配置 + 规则注入 | 数据 + Prompt | 略优 |
| 7 上线部署 | 部署 | **明显更麻烦** |

AI 编排代码约 **150–250 行**；CRUD、路由、页面、隔离、部署合计 **2000 行以上**。

> **AI 编排约占 15%，其余 85% 是标准 Web 工程。选型为 85% 服务。**

### 一条被忽略的证据

题目第二十三节明确列出「24H 内不建议花大量时间做」的清单，包含 **模型训练 / SFT / LoRA**。

> **题目排除掉的恰恰是 Python 最强的部分，要求交付的恰恰是 Web 栈的主场。**

## 3. 逐层说明

### 3.1 Next.js（App Router）

**为什么**：一个仓库同时交付页面和 API，把最大的交付风险（上线）压到最低。Route Handler 就是后端，将来要拆成独立服务也不用改前端契约。

| 约定 | 说明 |
|---|---|
| 所有 API 用 **Route Handler**，不用 Server Actions | 便于单测、便于 curl 排障、将来前端换实现不影响 |
| LLM 调用路由设置 `export const maxDuration = 60` | 防函数超时 |
| 服务端逻辑一律放 `src/server/` | 页面组件不直连数据库 |

| 陷阱 | 后果 |
|---|---|
| 在 Client Component 里 import `db.ts` | 打包进前端、连接数爆炸、潜在信息泄漏 |
| 环境变量用 `NEXT_PUBLIC_` 前缀 | **API Key 泄漏到浏览器**——最容易被抓的低级错误 |
| 在页面组件里裸写 `prisma.xxx` | 租户隔离边界被绕过 |

### 3.2 TypeScript

**为什么**：结构化输出的契约从「数据库列 → Prisma 类型 → Zod schema → API 响应 → 前端 props」是同一条链。用 Python 的话这条链会在 HTTP 边界断成两份定义（Pydantic ↔ interface），而**类型漂移正是结构化输出最容易出错的地方**。

| 约定 | 说明 |
|---|---|
| `strict: true` | 不开 strict 等于没用 TS |
| 禁止 `any`，必要时用 `unknown` + Zod 收窄 | 尤其处理 LLM 返回值时 |
| 共享类型放 `src/lib/types.ts` | 前后端引用同一份 |

### 3.3 Prisma

**为什么**：schema 文件本身就是数据设计文档，答辩时可以直接对着讲；migration + seed 一条命令；生成的类型直接用于业务代码。

| 约定 | 说明 |
|---|---|
| schema 单一来源 | 不手写建表 SQL |
| 本地用 `migrate dev`，线上用 `migrate deploy` | 后者不会尝试重置数据 |
| seed 必须可重复执行 | 用 `upsert` 而非 `create`，方便反复初始化 |

| 陷阱 | 后果 |
|---|---|
| 在循环里逐个查询 | N+1，页面上千次查询 |
| 忘记在 `where` 里带 `tenantId` | **跨租户数据泄漏** |
| 把 AI 调用放进事务 | 连接被占用十几秒，并发下直接耗尽连接池 |

### 3.4 LLM 接入层

**唯一的架构要求：只有 `src/server/agent/` 知道 LLM 存在。**

```ts
// src/server/agent/llm.ts
export type LLMResult =
  | { ok: true; raw: string; latencyMs: number; attempt: number }
  | { ok: false; error: string; latencyMs: number; attempt: number }

export async function callLLM(
  system: string,
  user: string,
  opts?: { timeoutMs?: number; retries?: number },
): Promise<LLMResult>
```

**这个签名是刻意的：它不抛异常，只返回联合类型。** 调用方必须显式处理失败分支，而不会因为一个未捕获的异常把整条链路打崩。

| 约定 | 值 |
|---|---|
| 单次超时 | 20s（应用层） |
| 重试次数 | 1 次，指数退避 |
| 修格式 | 非法 JSON 时抽取 `{...}` 重试 1 次 |
| 模型选择 | 环境变量 `LLM_MODEL`，默认 `deepseek-chat` |

#### 能力探测与降级（Q2 决定的落点）

兼容接口不一定支持 OpenAI 的 strict `json_schema`，所以**不能假设它支持**：

```text
① 优先请求 response_format: { type: 'json_schema', strict: true }
② 若返回 4xx 且错误提示与 response_format 相关
   → 记下能力标记，本进程内不再重试 strict
   → 降级为 response_format: { type: 'json_object' }
   → 并在 system prompt 里补一段「只输出 JSON，字段如下」的强约束
③ 无论走哪条路，返回值都必须过 Zod 校验
```

**这条降级路径顺手就把进阶挑战 3 的异常处理做掉了一半**——它本身就是"AI 一次调用失败不让项目崩溃"的一个实例。

#### 故障注入开关（Demo 用）

`callLLM` 读一个模块级开关，打开时**直接返回 `{ ok: false }`**，不真的发请求：

```ts
// 仅供 /dev 页面和测试使用，不暴露给业务代码
export function __setForceFailure(v: boolean) { forceFailure = v }
```

这是 `/dev` 页面三个工具之一，用来现场演示「AI 挂了系统不崩」。**不要用断网来演示**——现场不可控。

### 3.5 结构化输出（Zod）

```ts
export const AgentOutput = z.object({
  customer_intent: z.enum(['了解产品','询价','预约','犹豫','投诉','购买','其他']),
  lead_stage:      z.enum(['NEW','DISCOVERY','INTERESTED','HIGH_INTENT','WON','LOST']),
  next_action:     z.enum(['继续探需','回答问题','推进体验','确认需求','索取资料','转人工','暂不处理']),
  reply:           z.string().min(1).max(500),
  reason:          z.string().min(1),
  need_human:      z.boolean(),
  // 超出题目要求，但为可解释性加的两个字段
  rules_hit:       z.array(z.string()).default([]),
  confidence:      z.number().min(0).max(1).default(0.5),
})
```

**为什么要多两个字段**：

- `rules_hit` —— 把「租户规则确实影响了 AI」变成**可视化证据**，而不是嘴上说
- `confidence` —— 低置信度 + 高风险动作时降级转人工

**为什么动作空间必须是封闭枚举**：模型读的是不可信输入（客户消息），输出带着污染。封闭枚举 + 护栏，把最坏情况限制在「选错一个词」，而不是「执行了一个越界动作」。同时 7×6×2 是**有限可穷举空间**，每条分支都能写测试。

**枚举固定，但语义按租户覆盖。** `lead_stage` 的六个值是固定的（Zod 校验用），但它们在 prompt 里的**解释文本**来自 `tenant.config.stageDefs`：

```text
乐蒙    HIGH_INTENT = 已约好线下体验时间
机械之家 HIGH_INTENT = 已同意提供行驶证照片
```

所以「同一个客户问价，两个租户判出的阶段不同」是设计使然，不是模型抽风。**这也是核心任务 5 的一个可见证据。**

**跟进复用同一个 Schema。** 跟进调用（`trigger = 'FOLLOW_UP'`）返回的结构完全相同，只是 `next_action` 通常落在「推进体验 / 继续探需」上，且**结果不写回状态**（见 §9）。

### 3.6 样式

Tailwind 最简用法即可。题目第二十三节明确写了「精美 UI / 动画」不是重点。

**但有一条要坚持**：会话工作台的三栏布局要清晰，因为 Demo 要靠它一次性演示完整动线。

## 4. 为什么不是 Python + LangChain / LangGraph

### 4.1 一句话结论

> **LLM 在这道题里是系统的一个组件，不是系统的全部。**
> 判断依据：看 LLM 调用是「系统的一个函数」，还是「系统的核心循环」。本题是前者。

### 4.2 LangChain 的五个问题

公道话放在前面：**它省下的胶水代码（几十行）小于它带来的不确定性和不透明。**

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **抽象泄漏** | `LLMChain` / `AgentExecutor` 假设了「通用」。当你需要精确控制 prompt 每一段、重试条件、解析失败回退时，它反而有阻碍——要读源码才知道它拼了什么 |
| 2 | **API 不稳定** | 破坏性变更频繁。24H 里踩一次 breaking change，损失不可恢复的时间 |
| 3 | **调试不透明** | 默认会注入你没意识到的 system 文本、few-shot、格式指令。输出不符预期时，**无法确定是你的 prompt 问题还是框架包装问题** |
| 4 | **Token 成本不可控** | 框架注入的内容进计费 |
| 5 | **依赖体积 / 冷启动** | 拖进几十个传递依赖 |

**第 3 条直接伤害本题的得分点。** 题目要求 `reason` 要能解释判断依据，答辩要讲清「AI 为什么这么判」。本设计要求「发给模型的原文」是一等公民（记录在 `AgentRun.inputDigest` 可回放），**加一层框架正好破坏这个能力**。

### 4.3 LangGraph 的单独评估

LangGraph 和 LangChain 不是一回事，必须分开评价。

**先承认：概念确实对得上。**

| LangGraph 概念 | 本项目对应物 |
|---|---|
| State | `CustomerState` |
| Node | 组装上下文 / 调 LLM / 校验 / 更新状态 |
| Checkpointer | `CustomerState` 的历史版本 |
| `interrupt` | `need_human = true` |

所以「用 LangGraph 做这道题」不是荒谬的。**但有一个根本问题：**

> **LangGraph 的 checkpointer 持久化的是「流程执行状态」，存在框架自己的 store 里。
> 而这题需要的是「业务实体状态」——它必须能被业务代码直接用 SQL 查询。**

如果状态只活在 checkpoint 里，会失去：

```text
✗ 一条 SQL 查「本租户所有 HIGH_INTENT 客户」→ 客户列表页筛选排序
✗ 租户隔离的显式边界（checkpoint 表里没有 tenantId 语义）
✗ 销售在 UI 上直接修正状态（核心任务 4）
✗ 状态与 Message 的事务一致性
✗ 状态变更的审计与 version 递增
✗ 现场实战题「修改 Customer State」时能清楚指着代码讲
```

**正确的分层**：

```text
业务状态（CustomerState） →  自己的 Postgres，业务代码直接读写
流程编排（重试/中断/降级） →  可以用 LangGraph，也可以用 async 函数
```

**LangGraph 可以替换掉那个 60 行的 `analyze.ts`，但它绝不能替换掉 `CustomerState` 表。**

**另一个常见误解：LangGraph 本身不提供定时调度**（那是 LangGraph Platform）。所以就算上了它，Follow-up 的触发还是得自己解决。而 Follow-up 本质是「周期性扫状态」，不是「流程按步骤走」——用图模型表达周期扫描，是把工具用反了。

### 4.4 什么情况下结论反转

**一个选型结论必须给出证伪条件，否则就只是偏好。**

| 条件 | 为什么反转 |
|---|---|
| 要做**多智能体循环**（探需 ↔ 报价 ↔ 审核互相修正） | LangGraph 的主场 |
| 要做 **RAG**（检索历史成交案例、产品知识库） | Python 检索生态更厚 |
| 要做**离线评测 / 微调 / 数据分析** | 题目明确排除，若包含则无争议 |
| 需要**长时后台任务**（多轮跟进序列） | 常驻进程 + Celery 更自然 |
| **团队 / 面试方栈本身就是 Python** | 交付贴合对方环境，这是最强的选型理由 |

### 4.5 混合架构（如果一定要用 Python）

```text
┌──────────────────────┐        ┌──────────────────────┐
│ Next.js（Web + 业务） │  HTTP  │ FastAPI + LangGraph  │
│ · 页面 / CRUD / 隔离  │ ─────► │ · 只做 AI 编排        │
│ · CustomerState 读写  │        │ · 状态仍回写业务库    │
│ · Postgres（唯一业务库）│       └──────────────────────┘
└──────────────────────┘
```

契约只有一个：`POST /analyze` 收 `{history, state, tenantRules}`，返回 `AgentOutput`。

**代价要说清楚**：多一个部署目标、多一次网络跳转（失败模式增加）、多一份 schema 定义（Pydantic ↔ Zod 要同步）。

**24H 内这些代价换来的收益（更优雅的编排写法）不足以覆盖风险，所以基础部分不这么做。**

当前设计的三个可迁移点：

```text
① 编排入口唯一：analyzeCustomerMessage(tenantId, customerId, triggerMessageId)
② 步骤可拆：buildContext / buildPrompt / callLLM / validate / applyGuardrails / persist 都是纯函数
③ 业务状态与编排解耦：编排引擎可插拔，业务资产不可替换
```

迁移路径：`analyze.ts` 的线性编排 → LangGraph 图；**`CustomerState` 表保持不动**。

## 5. 架构分层与边界

```text
┌──────────────── 浏览器 ────────────────┐
│ Tenant 切换器 │ 客户列表 │ 会话工作台   │
└──────────────────┬─────────────────────┘
                   │ fetch
┌──────────────────▼─────────────────────┐
│ middleware.ts  单口令门锁（放行 /login） │
└──────────────────┬─────────────────────┘
                   │
┌──────────────────▼─────────────────────┐
│ Route Handlers                          │
│  第一行解析 tenantId                    │
├─────────────────────────────────────────┤
│ Service 层  customer / message / state  │
│  所有函数第一参数 = tenantId            │
├─────────────────────────────────────────┤
│ startup.ts  进程内定时器 → followup.ts   │
│  （常驻容器专属能力）                    │
├─────────────────────────────────────────┤
│ ★ agent/  ← 唯一知道 LLM 存在的模块      │
│  prompt → llm → schema → guardrails     │
│  analyze({ trigger: MESSAGE | FOLLOW_UP })│
├─────────────────────────────────────────┤
│ Prisma → PostgreSQL                     │
└─────────────────────────────────────────┘
                   │
            LLM API（OpenAI 兼容）
```

### 三条铁律

**① 只有 `agent/` 调 LLM。**
业务层调用的是 `analyzeCustomerMessage()` 这个普通函数。AI 挂了、超时了、返回垃圾了，都只是这个函数返回不同结果，不影响 CRUD 主链路。

**② 所有 service 函数签名以 `tenantId` 开头。**

```ts
// ✅ 让「忘记隔离」在类型层面变得很别扭
getCustomer(tenantId: string, customerId: string)

// ❌ 容易忘
getCustomer(customerId: string)
```

**③ 模型在物理上没有写库能力。**
它没有数据库连接、没有凭据、没有工具。`prisma.customerState.update` 这一行只存在于业务代码里。**模型提建议，代码执行。**

### 5.1 API 契约

| Method | Path | 说明 |
|---|---|---|
| GET | `/api/tenants` | 租户列表（顶部切换器） |
| GET / PATCH | `/api/tenants/:id` | 租户配置读取 / 演示时现场改规则 |
| GET | `/api/customers?tenantId=` | **必须带 tenantId** |
| POST | `/api/customers` | 创建客户 |
| GET | `/api/customers/:id?tenantId=` | 客户详情 + State + 消息 |
| POST | `/api/customers/:id/messages` | 写消息（CUSTOMER / SALES 通用），支持 `clientMsgId` 幂等 |
| POST | `/api/customers/:id/analyze` | 触发 AI 判定，返回建议卡片；按 `(customerId, triggerMessageId)` 幂等 |
| POST | `/api/customers/:id/reply` | 销售确认发送：落库 SALES 消息 + 更新状态 + 回填 `suggestionSent` |
| POST | `/api/customers/:id/resolve-human` | 解除人工（棘轮的必要出口） |
| GET | `/api/customers/:id/runs` | AgentRun 历史（排障 + Demo 讲审计） |
| POST | `/api/followups/scan` | 手动触发跟进扫描 |
| POST | `/api/auth` | 校验口令、种 cookie |

**约定：所有 handler 第一行解析 `tenantId`。** 这是让「忘记隔离」在类型层面变得别扭的第一道锁。

## 9. 编码约定

| 约定 | 原因 |
|---|---|
| service 函数以 `tenantId` 为第一参数 | 让忘记隔离变得别扭 |
| Route Handler 第一行解析 tenantId | 统一入口检查 |
| **LLM 调用不放在事务里** | 事务会被持有多秒，并发下耗尽连接池 |
| 所有时间存 UTC，展示时转本地 | 时区一致的唯一做法 |
| 判定的幂等靠数据库唯一约束 | 不靠应用层 if 判断 |
| 枚举常量进 `src/lib/constants.ts` | 阶段、动作只有一处定义 |
| **状态迁移只由客户的新输入驱动** | 跟进是我们主动说话，客户没提供新信息 |
| **跟进调用不写 `leadStage` / `intent`** | 只更新 `lastFollowUpAt` / `followUpCount`；否则会出现「发了句'考虑得怎么样'就把客户判成 HIGH_INTENT」 |
| 定时器注册用 `globalThis` 挂标记 | 防热重载 / 多 worker 重复注册 → 跟进重复 |
| `needHuman` 用 OR 不用覆盖 | 棘轮语义；AI 无权撤销人工状态 |
| Route Handler 第一行解析 tenantId | 统一入口检查 |

### 关键：LLM 调用与事务的边界

```text
错误做法
BEGIN → 调 AI（可能 15 秒）→ 写 4 张表 → COMMIT
        ↑ 写锁被持有 15 秒，并发下直接卡死

正确做法
调 AI（15 秒）→ BEGIN → 写 4 张表 → COMMIT
                 ↑ 事务只有几十毫秒
```

## 10. 开发时最容易犯的错（清单）

| # | 错误 | 后果 | 检查方式 |
|---|---|---|---|
| 1 | `where` 里忘带 `tenantId` | 跨租户数据泄漏 | 写测试：用租户 A 查租户 B 的 customerId，必须查不到 |
| 2 | API Key 用 `NEXT_PUBLIC_` 前缀 | 泄漏到浏览器 | 浏览器 Network 面板搜 key |
| 3 | 把 AI 调用放进事务 | 连接池耗尽 | 检查事务块的起止位置 |
| 4 | 取历史消息用 `asc + take 20` | 模型看不到最新消息 | 应该 `desc` 取完再 `reverse` |
| 5 | 在 Client Component 里 import `db` | 打包进前端 | 构建后检查 bundle |
| 6 | 循环里逐个查询（N+1） | 页面卡顿 | 用 `include` 或 `in` |
| 7 | `need_human` 用覆盖而不是 OR | 模型能撤销人工状态 | 业务上「谁能解除人工」必须明确 |
| 8 | 模型输出直接驱动副作用 | prompt 注入直达危害 | 所有写操作必须在 guardrails 之后 |
| 9 | 提交了 `.env` | 密钥泄漏 | `git log -p` 搜一遍 |
| 10 | seed 不可重复执行 | 反复初始化炸掉 | 用 `upsert` |
