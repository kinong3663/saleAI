# 租户配置改造方案

> 范围：把租户配置从「一半接线、一半摆设」改造成**全部接线 + 界面可编辑 + 产品报价可管理**。
>
> 前置：`改造方案.md` 第 6 节（本文档是它的详细版，可以直接替换那一节）
>
> 基于实测审计，不是设计推演。8 个 config 键 + 2 个租户列的实际生效情况见第 1 节。

---

## 0. 这份文档解决什么

现状是「**一半接线、一半摆设**」——这个状态在只有 `seed.ts` 能改配置时是安全的，因为改配置的人知道哪个键有用。

**但一旦开了配置界面，它立刻变成危险。**

```text
使用者在界面上改了 needHumanTriggers
→ 等了几轮，投诉的客户还是没转人工
→ 他会认为系统坏了
→ 更糟：他以为生效了，而投诉客户从来没被自动转人工过
```

> **「可编辑」不是暴露一个表单，是承诺「改了就会生效」。**
> 提供一个改了不生效的开关，比不提供更糟——它销毁的是对配置系统的信任。

**所以全篇的顺序原则是：先接线，再开界面。**

## 1. 现状审计（实测）

### 1.1 存储位置

```text
tenants 表
├─ salesGoal   （独立列 String）   "推动客户预约线下体验课。"
├─ tone        （独立列 String?）  "亲切、简短、口语化，不超过 80 字……"
└─ config      （JSONB，8 个键）
      rules[]              ← 规则文本 + 可选 enforcement
      stageDefs{}          ← 六个阶段的解释文本
      needHumanTriggers[]  ← 转人工触发词
      replyTone            ← （与上面 tone 重复）
      priceFallbackReply   ← 报价护栏兜底话术
      followUpAfterHours   ← 跟进阈值（乐蒙 24 / 机械 48）
      maxFollowUps         ← 跟进次数上限（都 2）
      products[]           ← 产品与价格
```

**没有数据库级 schema**（JSONB 的代价）：类型定义在 `src/lib/types.ts` 的 `TenantConfig`，读取时由 `tenant.service.getTenantForAgent()` 补默认值——少一个键不会炸，配错结构要到运行时才发现。

### 1.2 写入方

```text
唯一写入方：prisma/seed.ts（upsert by slug）
线上保护：SEED_ONLY_IF_EMPTY=true → 只在租户表为空时才写
没有任何 UI / API 能改配置
  PATCH /api/tenants/:id 和 /settings/tenant 在文档里列了，但都没实现
现在改配置只有两条路：
  改 seed.ts 重跑，或者直接改 JSONB（用 SQL）
```

### 1.3 生效情况（本次改造要处理的核心）

| config 字段 | 进 prompt？ | 谁在用 |
|---|---|---|
| `rules[].text` | ✅ | `prompt.ts` 第二节 |
| `rules[].enforcement` | — 不进 | `guardrails.ts` G3（唯一被代码执行的约束） |
| `stageDefs` | ✅ | `prompt.ts` 第三节 |
| `priceFallbackReply` | — 不进 | `analyze.ts`（护栏兜底话术） |
| `followUpAfterHours` / `maxFollowUps` | — 不进 | `followup.ts` |
| **`needHumanTriggers`** | ❌ | **没人读**——转人工全靠模型自由发挥 |
| **`products`** | ❌ | **没人读**——模型不知道体验课 198 |
| **`replyTone`** | ❌ | **没人读**（真正生效的是租户列 `tone`，两处语义重复） |

**三个死键，三种不同的处置**，见第 2 节。

## 2. P0 · 处理三个死键

### 2.1 `needHumanTriggers` → 接线 + 新增 G7 护栏

现在转人工完全靠模型自由发挥，**不确定**——同一个投诉，模型可能这次转、下次不转。接线后变成确定性的。

```text
G7 · 触发词强制转人工
  条件：本轮客户消息命中 tenant.config.needHumanTriggers 里任一词
  处置：need_human = true，next_action = '转人工'
```

三个设计细节：

```text
方向    单向强制。模型说 false 但触发词命中 → 强制改 true
        模型说 true 但没触发词    → 保持 true（棘轮语义）
        所以 G7 只加不减，和 needHuman 的 OR 棘轮一致

范围    只匹配「本轮客户消息」，不扫历史
        上一轮说要投诉 → 状态里已经 need_human=true，棘轮保住了
        不需要在 G7 里重复处理

匹配    中文用子串匹配（text.includes(trigger)）
        已知局限：「我不需要退款」会命中「退款」→ 写进 Known Issues
```

实现：

```ts
// guardrails.ts 内
const hitTrigger = ctx.tenant.config.needHumanTriggers
  .find(t => t && ctx.latestCustomerText.includes(t))

if (hitTrigger) {
  out.need_human = true
  out.next_action = '转人工'
  issues.push(`trigger_escalation:${hitTrigger}`)
}
```

**`issues` 里带上命中的具体触发词**，这样 UI 上能显示「因命中「投诉」转人工」，而不是一个没有理由的红灯。

### 2.2 `products` → 渲染进 prompt（有一个连带效果）

现在模型不知道体验课 198，只能空泛反问。渲染进去后它有了可依据的信息。

**但这里有个更重要的连带效果：**

> **G3 护栏之前可能是「空转」的。** 模型不知道准确价格，它编不出「198 元」这种具体数字，`CONCRETE_PRICE` 正则几乎匹配不到——**护栏根本没被真正考验过**。
>
> **渲染 products 之后，G3 才第一次面对真实的诱惑。**

所以接线 products 不只是"让模型有话说"，它同时**让报价护栏变得可达、变得可验证**。答辩时这个连带关系很值得讲。

### 2.3 `replyTone` → 删除，合并到 `Tenant.tone`

```text
Tenant.tone（独立列）        ✅ 实际渲染进 prompt
Tenant.config.replyTone     ❌ 没人读
```

**两处描述同一件事，正确做法是合并到唯一真源，不是二选一。** 而且 `tone` 是独立列——可查询、可索引、Prisma 类型明确，比 JSON 里的键更合适。

处理三步：

```text
① 从 TenantConfig 类型里移除 replyTone
② 从 seed.ts 里移除
③ 写一条一次性 SQL 清理线上 JSONB 里的残留（无害但保持干净）
   UPDATE tenants SET config = config - 'replyTone';
```

## 3. 产品与套餐报价（本次新增能力）

### 3.1 数据结构

```ts
export type QuotePolicy = 'AUTO' | 'HUMAN_ONLY'

export type TenantProduct = {
  id: string            // cuid。稳定标识，UI 编辑和 prompt 引用都用它
  name: string          // "亲子游泳体验课"
  price?: number        // 198。可选——有些产品必须评估后报价
  unit?: string         // "元/次"、"元/课时"
  description?: string  // "含 1 次体验课 + 1 次体质评估"
  quotePolicy?: QuotePolicy  // 默认 AUTO
  enabled?: boolean     // 默认 true，支持上下架
}
```

**为什么要有 `id`**：UI 编辑产品时需要一个稳定标识。如果靠 `name` 匹配，使用者改个名字就会把编辑状态搞乱——这是配置界面里最常见的一类 bug。成本几乎为零（cuid），但不加会踩坑。

**`price` 为什么可选**：机械之家的「保险理赔维修」必须技师看车才能给价。**没有价格的产品是合法状态**，不是缺数据。

### 3.2 报价的两个维度（这是本次改造的核心设计）

```text
时间维度    什么时候允许报价      ← 由规则决定（R1 的 enforcement）
对象维度    哪些产品允许报价      ← 由产品决定（quotePolicy）
```

**这两个维度是独立的，而且都是真实的商业需求**：

```text
时间维度    "客户没表达兴趣前不报价"
            ——乐蒙的 R1，逼销售先建立需求再谈钱

对象维度    "体验课 198 可以随口报，课包 4680 必须人工谈"
            ——引流品和大单的价格敏感度完全不同
```

**只有时间维度的系统，会给所有产品一样的报价权限**——这在真实销售里是不成立的。体验课报价是获客手段，大单报价会毁掉谈判空间。

### 3.3 进 prompt 的格式

```text
## 产品与报价（内部资料，用于准确回答客户）
- [P1] 亲子游泳体验课 — 198 元/次
       含 1 次体验课 + 1 次体质评估
- [P2] 24 课时课包 — 4,680 元（合 195 元/课时）
       含 24 次课 + 阶段性评估
- [P3] 保险理赔维修 — 需评估后报价

## 报价规则（重要）
上表是真实价格，但**是否可以说出口由「企业销售规则」决定**：
- 如果规则禁止报价，不要说出任何具体数字，改为引导
- 只允许使用上表中的价格，**不要计算、推测或编造任何价格**
- 客户问及上表没有的产品，如实说「这个我需要确认一下」，不要猜
```

**最后三条必须写**：

```text
第二条    模型知道多个价格后会"心算"（"课包 24 课时合下来每课时更便宜"）
          这类推导出的数字也是编造，也会引起纠纷
第三条    空泛反问是"不知道"，编造价格是"给错承诺"——后者严重得多
```

`enabled === false` 的产品不进 prompt（上下架生效）。

### 3.4 护栏升级

**G3 改写为双维度检查：**

```ts
for (const rule of ctx.rules) {
  const e = rule.enforcement
  if (!e) continue

  // 不认识的 kind 不静默跳过 —— 见第 6 节
  if (e.kind !== 'FORBID_PRICE_UNTIL') {
    issues.push(`unknown_enforcement_kind:${rule.id}`)
    continue
  }

  // 时间维度：条件已满足 → 允许报价
  if (isConditionMet(e.condition, out, ctx)) continue

  // 时间维度未满足 → 任何具体价格都不许说
  if (extractPrices(out.reply).length > 0) {
    issues.push('price_rule_violated')
    out.rules_hit = [...new Set([...out.rules_hit, rule.id])]
    needsRegen = true
  }
}

// 对象维度：HUMAN_ONLY 的产品，即使时间条件满足也不许报
const humanOnlyPrices = new Set(
  ctx.tenant.config.products
    .filter(p => p.enabled !== false && p.quotePolicy === 'HUMAN_ONLY')
    .map(p => p.price)
    .filter((n): n is number => typeof n === 'number'),
)

if (extractPrices(out.reply).some(n => humanOnlyPrices.has(n))) {
  issues.push('human_only_price_leaked')
  out.need_human = true
  out.next_action = '转人工'
  needsRegen = true
}
```

**新增 G8 · 禁止编造价格：**

```ts
const knownPrices = new Set(
  ctx.tenant.config.products
    .filter(p => p.enabled !== false)
    .map(p => p.price)
    .filter((n): n is number => typeof n === 'number'),
)

const fabricated = extractPrices(out.reply).filter(n => !knownPrices.has(n))
if (fabricated.length > 0) {
  issues.push(`fabricated_price:${fabricated.join(',')}`)
  needsRegen = true
}
```

价格提取函数（**用数值比较，不用子串**）：

```ts
function extractPrices(text: string): number[] {
  return [...text.matchAll(/(\d[\d,]*)\s*元/g)]
    .map(m => Number(m[1].replace(/,/g, '')))
}
```

⚠️ **必须用数值比较**。`'1980'.includes('198')` 是 `true`——如果用字符串包含判断，「1980 元」会被误认为合法价格 198。

**G8 会有误报吗？会，而且是设计使然。**

```text
模型说"原价 398，现在 198" → 398 不在 products 里 → 判定为编造 → 打回
```

**这是正确行为**：如果 398 不在配置里，模型确实是编的。要么把它配进产品表，要么不许说。**打回重生成比放行一个编造的价格安全得多。**

## 4. 配置读写 API

### 4.1 用 PUT 不用 PATCH

```text
PUT /api/tenants/[id]/config     用这份完整配置替换当前配置
```

原文档写的是 `PATCH`，**建议改成 PUT**。理由：PATCH 语义是"部分更新"，但 `rules` 是数组——部分更新时到底是替换还是追加？语义不清。**整段替换最可预测**，也避免深合并的歧义（数组的深合并规则几乎总会让人意外）。

### 4.2 校验 schema

```ts
const ProductSchema = z.object({
  id:          z.string().min(1),
  name:        z.string().min(1).max(60),
  price:       z.number().nonnegative().optional(),
  unit:        z.string().max(20).optional(),
  description: z.string().max(200).optional(),
  quotePolicy: z.enum(['AUTO', 'HUMAN_ONLY']).default('AUTO'),
  enabled:     z.boolean().default(true),
})

const TenantConfigSchema = z.object({
  rules: z.array(z.object({
    id:     z.string().min(1).max(10),
    type:   z.enum(['PROHIBIT', 'REQUIRE', 'PREFER']),
    text:   z.string().min(1).max(300),
    enforcement: z.object({
      kind:      z.enum(ENFORCEMENT_KINDS),        // ★
      condition: z.enum(ENFORCEMENT_CONDITIONS),   // ★
    }).optional(),
  })).max(10)
    .refine(rs => new Set(rs.map(r => r.id)).size === rs.length,
            { message: '规则 ID 不能重复' }),

  stageDefs: z.record(z.enum(LEAD_STAGES), z.string().min(1)),   // ★

  needHumanTriggers:  z.array(z.string().min(1)).max(10),
  priceFallbackReply: z.string().min(1).max(200),
  followUpAfterHours: z.number().int().min(1).max(720),
  maxFollowUps:       z.number().int().min(0).max(10),

  products: z.array(ProductSchema).max(20)
    .refine(ps => new Set(ps.map(p => p.id)).size === ps.length,
            { message: '产品 ID 不能重复' })
    .refine(ps => new Set(ps.map(p => p.name)).size === ps.length,
            { message: '产品名称不能重复' }),
})
```

### 4.3 三个必查项，每一个对应一个具体故障

| 校验 | 防的是什么故障 |
|---|---|
| `kind` / `condition` 用 `z.enum` | **护栏静默失效**——存进不认识的 kind，G3 会 `continue` 跳过 |
| `stageDefs` 用 `z.record(z.enum(LEAD_STAGES))` | 漏一个阶段 → prompt 里出现 `undefined` → 模型输出随机 |
| 规则 ID / 产品 ID / 产品名称唯一 | `rules_hit` 分不清哪条规则命中；产品列表编辑状态错乱 |

**这三条是整份文档最关键的地方。** 没有它们，配置界面就是破坏系统的入口。

## 5. 配置界面

`/settings/tenant`，分区编辑：

```text
基本信息      name / industry / salesGoal / tone
规则列表      增删改；每条含 类型下拉 + 文本 + 自动约束下拉
阶段定义      6 个固定输入框（没有「删除」按钮）
转人工触发词  标签式输入
跟进阈值      数字输入（小时 / 次数）
产品与报价    列表：名称 / 价格 / 单位 / 说明 / 报价策略 / 上下架
兜底话术      文本框
底部          保存按钮 + 校验错误列表 + 「最后修改于 X」
```

### 5.1 一条界面设计原则：让非法状态无法产生

| 字段 | 界面形态 | 为什么 |
|---|---|---|
| 阶段定义 | **6 个固定框，无删除按钮** | 结构上不可能漏 |
| 规则 ID | 自动生成（R1、R2…） | 结构上不可能重复 |
| 规则类型 | 下拉 | 不可能输入非法值 |
| 自动约束 | **下拉的「约束模板」** | 见下 |
| 产品 ID | 新建时自动生成，不可编辑 | 改名不会破坏引用 |

### 5.2 别把技术枚举直接暴露给使用者

不要给两个下拉让人选 `kind` 和 `condition`——**那是把实现细节丢给业务人员**。包装成业务语言：

```text
自动约束：
  ○ 不施加自动约束
  ○ 禁止报价，直到客户表达明确兴趣      → { FORBID_PRICE_UNTIL, INTEREST_EXPRESSED }
  ○ 禁止报价，直到客户提供资料          → { FORBID_PRICE_UNTIL, DOCUMENT_CONFIRMED }
```

**一个下拉，内部映射到 kind + condition 组合。** 使用者在选业务意图，不是在拼字符串。

而且这样一来，**加一个新的约束种类 = 在映射表里加一行 + 写一条护栏分支**，界面自动多一个选项。

### 5.3 产品编辑区的关键交互

```text
新增产品    自动生成 id，弹出编辑行
删除产品    二次确认（价格数据丢了要重填）
上下架      开关，不删数据（历史 AgentRun 里引用过的产品还在）
报价策略    下拉「自动报价 / 仅人工报价」，默认自动

价格留空    允许。留空表示「需评估后报价」
            界面上显示提示：「留空则 AI 不会报价，会引导客户提供资料」
```

**最后那条提示很重要**——它把"留空"这个设计的后果直接告诉使用者，避免他以为留空是没填完。

## 6. 审计与可观测

### 6.1 你已经有 `AgentRun.inputDigest`，最重要的那件事已经做好了

```text
inputDigest 存了发给模型的原文 → 规则文本、产品价格都在里面 → 历史判定可回放
```

**所以不需要单独的 configVersion 来保证可解释性。** 版本号只能多做一件事：可查询（"哪些判定是在 R1 修改前产生的"）。24H 内可以不做。

### 6.2 要补的两件

```text
① Tenant.updatedAt 自动更新，界面显示「最后修改于 X」
   成本 0，但它让"配置什么时候变的"有了答案

② README 写：生产环境应记配置变更日志（谁、何时、改前改后）
   用文档声明代替代码实现——题目明确允许
```

### 6.3 让静默失效留有痕迹（防御纵深）

即使有了 Zod 校验，护栏里仍要留一条：

```ts
if (e.kind !== 'FORBID_PRICE_UNTIL') {
  // 不静默 continue
  issues.push(`unknown_enforcement_kind:${rule.id}`)
  continue
}
```

记进 `AgentRun.guardrailIssues`。

**为什么值得留？你自己就是例子。** 你做 S4 双租户对照时，是**用 SQL 直接改了 R1 的 `condition`**——绕过了所有界面和 API 校验。

> **只要有人能直连数据库，就只有运行时的可观测性能兜住。**

而"静默失效"最难查的地方在于：界面上一切正常，审计里也一切正常，**你根本不知道该去看什么**。留一条 `guardrailIssues` 就等于给未来埋了一个搜索锚点。

## 7. 改造顺序与验收

```text
P0-0  处理三个死键（必须在开界面前）
        needHumanTriggers  → 接线 + G7
        products           → 渲染进 prompt（激活 G3）
        replyTone          → 删除，合并到 Tenant.tone

P1    产品数据模型 + 护栏升级（G3 双维度 + G8）

P2    配置读写 API（PUT）+ Zod 校验

P3    /settings/tenant 界面（约束模板下拉 + 固定阶段框 + 产品编辑区）

P4    updatedAt 显示 + README 写审计方案

P5    未知 enforcement kind 写入 AgentRun.guardrailIssues

P6    回归
```

### 每步验收

| 步骤 | 验收 |
|---|---|
| P0-0 | 说「我要投诉」→ 必转人工且 `guardrailIssues` 有 `trigger_escalation:投诉`；prompt 里能看到产品价格 |
| P1 | 编造一个不存在的价格 → 被 G8 打回；说 HUMAN_ONLY 产品的价格 → 强制转人工 |
| P2 | 提交 `enforcement.kind` 非法 → 保存被拒；删掉一个阶段定义 → 保存被拒 |
| P3 | 现场改产品价格 198 → 298 → 重新提问，AI 报出新价格 |
| P5 | 用 SQL 直接把 kind 改成瞎写 → 下一次判定 `guardrailIssues` 里有 `unknown_enforcement_kind` |
| P6 | 重跑双租户对照、投诉转人工、报价护栏、follow-up |

**P0-0 不能和 P3 颠倒。** 先开界面就是在提供一个改了不生效的开关。

## 8. 答辩要点

### 8.1 证据升级

补完之后，「切换租户 AI 行为不同」这条证据从"规则文本变了"升级到**三处**：

```text
规则文本      R1–R3 在两个租户下完全不同
转人工策略     投诉/要真人 → 确定性转人工（G7），不再靠模型自由发挥
可报价范围     产品信息 + 报价策略 + G3/G8，两个租户的可报价边界真正不同
```

**后两处是质变**——它们从"模型可能这么判"变成了"代码保证这么判"。这才是题目要的「确定性业务规则」。

### 8.2 三个必答题

**「租户配置能改到什么程度？」**

> 策略层可配：规则、阶段语义、触发词、阈值、产品与报价。
> 契约层不可配：阶段枚举的 6 个值、意图与动作枚举、护栏种类。
> **契约变更是版本升级，不是配置变更**——加第 7 个阶段要改枚举、Zod schema、前端映射，还要处理存量数据的非法值。这是发版本的事，不是配界面的事。

**「如果租户把配置改坏了怎么办？」**

> 三层防护：界面不给非法输入的可能（阶段 6 个固定框、约束用模板下拉）；
> 服务端 Zod 强校验（枚举、覆盖完整性、ID 唯一）；
> 运行时留痕（不认识的 enforcement kind 记进 `AgentRun.guardrailIssues`）。
> **配置系统最典型的失败模式是"静默失效"——界面上一切正常，但护栏已经不工作了。** 这三层分别防手误、防绕过、防未知。

**「报价为什么还分产品？」**

> 因为报价有两个独立维度：**时间维度**（什么时候能报）和**对象维度**（哪些能报）。
> 体验课 198 是引流品，随口报反而是获客手段；课包 4680 是大单，提前报价会毁掉谈判空间。
> 只有时间维度不够用——那会给所有产品一样的报价权限。

### 8.3 现场演示（30 秒版）

```text
① 打开 /settings/tenant，展示乐蒙的「亲子游泳体验课 198 元」
② 会话里客户问「体验课多少钱？」→ AI 回答 198 元
③ 回配置页把价格改成 298
④ 再问一次 → AI 回答 298 元              ← 证明产品数据是活的

⑤ 现场加一个「24 课时课包 4680 元」，报价策略选「仅人工」
⑥ 客户问「课包多少钱？」→ AI 不报 4680，转而引导   ← 证明报价策略生效
```

**第 ③④ 步证明配置是活的；第 ⑤⑥ 步证明策略是分层的。** 两个加在一起，比展示两个租户的预设差异有说服力得多——因为它是现场的、可逆的。
