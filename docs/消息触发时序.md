# 消息触发时序（B+C 方案）

> 范围：客户发消息后，AI 建议**由谁触发、什么时候触发、怎么保证只触发一次**。
>
> 前置：`双账号方案.md`（双面 UI 与账号）
>
> 本方案的价值不在功能，在**时序正确性**——它决定了「客户发完消息，客服端多久看到建议」以及「会不会重复烧钱」。

---

## 1. 一个让实现变简单的决定

先改 `analyze` 的签名：

```ts
// ❌ 旧的：调用方要传"分析哪条消息"
analyzeCustomerMessage(tenantId, customerId, triggerMessageId)

// ✅ 新的：调用方只管"分析这个客户"，分析哪条由函数内部决定
analyzeCustomerMessage({ tenantId, customerId })
```

**为什么这个改动很重要**：

```text
B 路径（服务端后台）和 C 路径（客服端兜底）会调用同一个函数。
如果 triggerMessageId 由调用方传入，两条路径可能传不同的值 → 
产生两条 AgentRun → 重复调 LLM。

改成内部决定之后：
  两条路径的调用签名完全一致 → 不可能不一致
  "当前该分析哪条"只有一个地方判断 → 不可能不一致
```

**把幂等键的判定收进被调用方，而不是交给调用方。** 这是消除一整类时序 bug 的办法。

## 2. 完整链路

```text
客户                服务端                          客服端
 │                    │                              │
 ├─ POST /chat/msg ──►│                              │
 │                    ├─ 落库 Message（同步）        │
 │◄── 200 "已发送" ───┤                              │
 │                    │                              │
 │                    └─ after(): scheduleAnalyze()  │  ← B 路径
 │                        防抖 3 秒                  │
 │                        静默后 runOnce()           │
 │                          ├─ 内存锁（防重入）      │
 │                          ├─ 读最后一条客户消息    │
 │                          ├─ 幂等检查（AgentRun）  │
 │                          ├─ 调 LLM（5-15s）       │
 │                          └─ 事务写 AgentRun+State │
 │                    │                              │
 │                    │◄── 轮询 /messages（2.5s）────┤
 │                    ├─ { messages, suggestion,     │
 │                    │    analysisState } ─────────►│
 │                    │                              ├─ 显示建议卡片
 │                    │                              │
 │                    │◄── 若 PENDING 则触发 ────────┤  ← C 路径
 │                    └─ runOnce()（同上，被内存锁拦住或幂等拦住）
 │                    │                              │
 │◄─ 轮询 /chat/msg ──┤                              │
 │   （只有消息，无 AI 内容）                        │
```

## 3. 调度器实现

新建 `src/server/agent/scheduler.ts`。

```ts
import { analyzeCustomerMessage } from './analyze'

const DEBOUNCE_MS = 3000

// 进程内状态 —— 因为部署在常驻单实例容器里，这两个 Map/Set 是可靠的
const timers   = new Map<string, NodeJS.Timeout>()
const inFlight = new Set<string>()

const keyOf = (tenantId: string, customerId: string) => `${tenantId}:${customerId}`

/**
 * B 路径：客户发消息后调用。带防抖。
 * 客户连发 5 条 → 前 4 个定时器被取消 → 只跑最后一次。
 */
export function scheduleAnalyze(tenantId: string, customerId: string) {
  const k = keyOf(tenantId, customerId)

  const prev = timers.get(k)
  if (prev) clearTimeout(prev)          // ★ 防抖核心：取消上一次

  timers.set(k, setTimeout(() => {
    timers.delete(k)
    void runOnce(tenantId, customerId)
  }, DEBOUNCE_MS))
}

/**
 * C 路径：客服端兜底触发。无防抖，但要防重入。
 * @returns 判定结果；若本进程已在处理同一客户，返回 null
 */
export async function runOnce(tenantId: string, customerId: string) {
  const k = keyOf(tenantId, customerId)

  if (inFlight.has(k)) return null       // ★ 本进程已在跑 → 直接放弃
  inFlight.add(k)

  try {
    return await analyzeCustomerMessage({ tenantId, customerId })
  } catch (err) {
    // 后台任务绝不能让异常冒出去
    console.error('[analyze] failed', { tenantId, customerId, err })
    return null
  } finally {
    inFlight.delete(k)
  }
}
```

### 3.1 为什么用内存锁而不是数据库占位

两条路：

| 做法 | 说明 | 代价 |
|---|---|---|
| 数据库占位行 | 先插一条 `status=RUNNING` 的 AgentRun 当锁 | 要处理"占位后崩溃"的僵尸行，需要超时清理 |
| **内存锁** ⭐ | `Set<string>` + 提前 `return` | 多实例部署时失效 |

**选内存锁**，因为它和这个项目的部署形态匹配：**常驻单实例容器**。这跟 Follow-up 用进程内 `setInterval`、防抖用 `Map + setTimeout` 是同一套思路——**同一个部署决策带来的三个架构自由度**。

而数据库唯一约束作为**最终防线**（见第 4 节），兜住进程重启后的一致性问题。

**答辩口径**：并发控制有主有辅——主是进程内锁（覆盖单实例的绝大多数竞态），辅是数据库唯一约束（覆盖重启和多实例的边缘情况）。**如果将来要多实例，只需把内存锁换成 Redis 锁，唯一约束不用动。**

## 4. `analyze.ts` 的改动

```ts
export async function analyzeCustomerMessage(input: {
  tenantId: string
  customerId: string
  trigger?: TriggerKind     // 默认 CUSTOMER_MESSAGE；Follow-up 时传 FOLLOW_UP
}) {
  const { tenantId, customerId, trigger = 'CUSTOMER_MESSAGE' } = input

  // ① 当前最后一条客户消息（由本函数决定，不由调用方传）
  const last = await prisma.message.findFirst({
    where: { tenantId, customerId, role: 'CUSTOMER' },
    orderBy: { createdAt: 'desc' },
    select: { id: true },
  })
  if (!last) return null

  // ② 幂等检查
  const existing = await prisma.agentRun.findUnique({
    where: { customerId_triggerMessageId: { customerId, triggerMessageId: last.id } },
    select: { status: true, output: true },
  })
  if (existing) return existing.output        // 已分析过 → 直接返回旧结果

  // ③ 组装上下文 → 调 LLM → Zod 校验 → 护栏
  //    ★ 注意：整个过程在事务之外（LLM 可能跑十几秒）
  const { output, issues, needsRegen, raw, latencyMs, model, inputDigest } = await runPipeline(...)

  // ④ 事务写入：AgentRun + CustomerState 原子提交
  try {
    await prisma.$transaction(async tx => {
      await tx.agentRun.create({
        data: {
          tenantId, customerId,
          trigger,
          triggerMessageId: last.id,
          status, model, latencyMs, inputDigest,
          rawOutput: raw, output,
          rulesHit: output.rules_hit,
          guardrailIssues: issues,
        },
      })
      if (trigger === 'CUSTOMER_MESSAGE') {
        await applyStateUpdate(tx, { tenantId, customerId, output, prev })   // 决策 Q13
      }
    })
  } catch (err) {
    // ★ 唯一约束兜底：并发时后写入方会撞唯一约束
    if (isUniqueViolation(err)) {
      const winner = await prisma.agentRun.findUnique({
        where: { customerId_triggerMessageId: { customerId, triggerMessageId: last.id } },
        select: { output: true },
      })
      return winner?.output ?? null
    }
    throw err
  }

  return output
}
```

**第 ④ 步的 `catch` 不能省**：它是并发时的兜底路径。撞了唯一约束说明别人先写成功了，读它的结果返回即可——**语义上完全正确，因为两条路径分析的是同一条消息**。

## 5. 客户侧接口

```ts
// app/api/chat/messages/route.ts
export async function POST(req: Request) {
  const { tenantId, customerId } = await requireCustomer()   // ★ tenantId 来自服务端
  const body = await req.json()

  const message = await prisma.message.create({
    data: {
      tenantId, customerId,
      role: 'CUSTOMER',
      content: body.content ?? '',
      attachments: body.attachments ?? null,
      clientMsgId: body.clientMsgId ?? null,     // 幂等：前端重发不产生重复
    },
  })

  // ★ 客户已经拿到响应，这里继续跑
  after(() => { scheduleAnalyze(tenantId, customerId) })

  return NextResponse.json({ ok: true, messageId: message.id })
}
```

**用 Next 15 的 `after()`，不要用裸的 `void fn()`。** 裸写法在异常时是 unhandled rejection，可能把进程带下去；`after()` 会正确接管生命周期。

客户侧的轮询接口只返回消息，**不含任何 AI 字段**：

```ts
// GET /api/chat/messages?after=<msgId>
export async function GET(req: Request) {
  const { tenantId, customerId } = await requireCustomer()
  const after = new URL(req.url).searchParams.get('after')

  const rows = await prisma.message.findMany({
    where: {
      tenantId, customerId,
      ...(after ? { createdAt: { gt: await createdAtOf(after) } } : {}),
    },
    orderBy: { createdAt: 'asc' },
    take: 50,
  })

  return NextResponse.json({ messages: rows.map(toCustomerMessage) })   // 白名单 DTO
}
```

## 6. 客服侧接口

轮询接口要额外返回分析状态——**这是 C 路径能工作的前提**。

```ts
// app/api/customers/[id]/messages/route.ts
export async function GET(req: Request) {
  const { tenantId } = await requireAgent()
  const { id: customerId } = await params

  const messages = await listMessagesSince(tenantId, customerId, after)

  // 判断当前分析状态
  const lastCustomerMsg = await prisma.message.findFirst({
    where: { tenantId, customerId, role: 'CUSTOMER' },
    orderBy: { createdAt: 'desc' },
    select: { id: true },
  })

  let analysisState: 'IDLE' | 'PENDING' | 'DONE' | 'FAILED' = 'IDLE'
  let pendingFor: string | null = null

  if (lastCustomerMsg) {
    const run = await prisma.agentRun.findUnique({
      where: { customerId_triggerMessageId: { customerId, triggerMessageId: lastCustomerMsg.id } },
      select: { status: true, output: true },
    })

    if (!run) {
      analysisState = 'PENDING'
      pendingFor = lastCustomerMsg.id
    } else if (run.status === 'SUCCESS' || run.status === 'REPAIRED') {
      analysisState = 'DONE'
    } else {
      analysisState = 'FAILED'          // FALLBACK 也走这条分支
    }
  }

  return NextResponse.json({ messages, suggestion, analysisState, pendingFor })
}
```

### 6.1 前端轮询

```ts
export function useCustomerPolling(customerId: string) {
  const [messages, setMessages] = useState<Message[]>([])
  const [suggestion, setSuggestion] = useState<Suggestion | null>(null)
  const [analysisState, setAnalysisState] = useState<AnalysisState>('IDLE')

  const lastIdRef      = useRef<string | null>(null)
  const triggeredForRef = useRef<string | null>(null)   // ★ 已为哪条消息触发过兜底

  useEffect(() => {
    let alive = true

    async function tick() {
      const res = await fetch(
        `/api/customers/${customerId}/messages?after=${lastIdRef.current ?? ''}`,
      )
      if (!res.ok || !alive) return
      const data = await res.json()

      if (data.messages?.length) {
        setMessages(prev => [...prev, ...data.messages])
        lastIdRef.current = data.messages[data.messages.length - 1].id
      }
      setSuggestion(data.suggestion ?? null)
      setAnalysisState(data.analysisState)

      // ★ C 路径：同一条消息只触发一次
      if (data.analysisState === 'PENDING'
          && data.pendingFor
          && triggeredForRef.current !== data.pendingFor) {
        triggeredForRef.current = data.pendingFor
        fetch(`/api/customers/${customerId}/analyze`, { method: 'POST' })
      }
    }

    tick()
    const t = setInterval(tick, 2500)
    return () => { alive = false; clearInterval(t) }
  }, [customerId])

  return { messages, suggestion, analysisState }
}
```

**`triggeredForRef` 是关键**——没有它，每次轮询（2.5 秒一次）都会触发一次 analyze。用"已为哪条消息触发过"做标记，既不重复触发，新消息来了又能触发。

## 7. 客服端的三态 UI

```text
analysisState = 'DONE'     →  显示 AI 建议卡片（意图/阶段/动作/命中规则/reply）
analysisState = 'PENDING'  →  显示「AI 分析中…」+ 骨架屏
analysisState = 'FAILED'   →  显示「AI 暂不可用，已转人工」+ 红灯
analysisState = 'IDLE'     →  不显示建议区
```

**为什么 PENDING 必须显式显示**：

```text
不显示 → 客服等 2 秒没反应 → 会怀疑系统坏了、或者自己再点一次发送
显示「分析中…」→ 客服知道系统在工作，而且这本身就在展示"实时协作"
```

**为什么 FAILED 不能停在"分析中"**：那会把一次**可恢复的失败**显示成**系统卡死**。fallback 必须写进 `AgentRun.status` 并让前端读到。

## 8. 防抖的副作用（要写进 README）

3 秒防抖意味着「一段时间内的连续消息被合并成一轮」：

```text
客户发：「你好」「在吗」「多少钱」（间隔 1 秒）
→ 只分析 1 次
→ triggerMessageId = 「多少钱」那条
→ 但三条都在历史里，模型看得到全部 ✓

客户发一条，10 秒后又发一条
→ 触发 2 次分析
→ 这是"两轮对话"，行为正确 ✓
```

**防抖天然完成了对话分段** —— 它把"客户一口气说完的话"归为一轮，"隔着停顿说的话"分成两轮。这和真人阅读习惯一致。

局限（写进 Known Issues）：

```text
· 进程重启会丢定时器 → 靠 C 路径和 follow-up 扫描自愈
· 多实例部署会失效   → 那时需要 Redis
· triggerMessageId 只记最后一条 → 审计上看不到"这轮还有前两条"
  但 inputDigest 里存了完整历史，可回放
```

## 9. 验收清单

```text
触发与去重
[ ] 客户发一条消息 → 3 秒内客服端出现建议卡片         （B 路径）
[ ] 客户连发 3 条（间隔 1 秒）→ 只产生 1 条 AgentRun   （防抖生效）
[ ] 注释掉 scheduleAnalyze 调用 → 客服端仍能出建议     （C 兜底生效）
[ ] 两个浏览器窗口同时打开同一客户 → 只产生 1 条 AgentRun（内存锁生效）
[ ] 手工插一条重复的 AgentRun 请求 → 撞唯一约束，走 catch 分支返回旧结果

状态与 UI
[ ] 建议生成前，客服端显示「AI 分析中…」而不是空白
[ ] 打开 /dev 的强制故障开关 → 客服端显示「AI 暂不可用，已转人工」，不停在分析中
[ ] 客户侧的轮询响应里搜不到 suggestion / stage / rules_hit / analysisState

回归
[ ] 客户发消息后刷新客服页，历史消息和建议都还在
[ ] Follow-up 触发（trigger=FOLLOW_UP）不写 leadStage（决策 Q13）
```

**第 3 条（注释掉 B）和第 4 条（双窗口）不能省**——它们分别证明 C 兜底和内存锁真的在工作。不测的话，你不知道这两层是不是只是摆设。

## 10. 答辩要点

**「客户发完消息，客服端多久看到建议？」**

> 正常 5–20 秒：3 秒防抖 + 模型调用时间。
> 这段时间客服端显示「AI 分析中…」——**不让客服看到空白**，因为空白会被理解成系统坏了。

**「如果服务端的自动分析失败了怎么办？」**

> 客服端轮询时如果发现「有客户消息但没有 AgentRun」，会兜底触发一次。
> 所以是 **B（服务端自动）+ C（客服端兜底）双路径**，任一条成功即可。
> 两者都命中时，进程内锁和数据库唯一约束保证只分析一次。

**「为什么不用 Redis 做锁和防抖？」**

> 因为部署在常驻单实例容器上，进程内的 `Set` 和 `Map` 就是可靠的。
> 这跟 Follow-up 用进程内 `setInterval` 是同一个判断——**部署形态决定了架构自由度**。
> 数据库唯一约束作为最终防线兜住重启的边缘情况。要多实例时，只需把内存锁换成 Redis 锁。

**「怎么保证不重复烧钱？」**

> 三层：进程内锁（防同一进程重入）→ 幂等检查（防已分析过的消息）→ 唯一约束（防并发写入）。
> 前两层覆盖 99% 的情况，第三层是兜底——**即使前两层都失效，也只是多调一次 LLM，审计记录仍然只有一条**。
