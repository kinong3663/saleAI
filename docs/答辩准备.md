## 2. README 预填（题目第二十五节的八个问题）

**不要写成长篇报告**，每节三两句话即可。

### 1. 你做了什么

一句话：让 AI 读历史对话 + 客户状态 + 企业销售规则，输出结构化销售判断；销售确认或修改后发送，结果落库并参与下一轮判断。

### 2. 系统架构

贴 `技术栈构建与说明.md` 第 5 节的架构图。重点讲一件事：**只有 `src/server/agent/` 知道 LLM 存在**，其余业务代码调用的是普通函数。

### 3. 主要数据结构

贴 `数据表构建与说明.md` 第 4 节的 schema。重点讲两张表为什么单独存在：

```text
CustomerState  唯一可变的业务状态，同时是 AI 输入、UI 数据源、人工可编辑对象
AgentRun       AI 决策的黑匣子，让不可复现的模型调用变成可回放的数据
```

### 4. AI Pipeline

一条客户消息进来后依次发生：读旧状态 → 组装上下文（历史 + 状态 + 租户规则）→ 调 LLM 取结构化输出 → Zod 校验 → **确定性护栏裁决** → 写 AgentRun + 更新 CustomerState（同一事务）。

重点讲**护栏**和**幂等**，它们是这个系统区别于 ChatGPT Wrapper 的地方。

### 5. Assumptions

```text
单客服场景，不做客户分配
微信未接入，客户消息由人工录入模拟
AI 不自动发送，必须销售确认
时间统一存 UTC，展示转本地
对话上下文固定取最近 20 条，未做动态 token 预算
两个租户的规则、阶段语义、跟进阈值均可配置
```

### 6. Trade-offs

**直接搬 `决策记录.md` 第 4 节的八条放弃清单**，那里每条都带了原因和替代写法。核心一句话：

> 24H 内优先保证核心链路可运行、可解释，需要引入新基建的能力（Redis 回合缓冲、消息队列、RLS）只写方案不实现。

### 7. Known Issues

```text
LLM 输出质量与延迟不可控，已用 fallback 兜底但会影响体验
连续消息未做生产级聚合，快速连发会触发多次判定
租户规则的硬校验是关键字 / 正则，不是通用规则引擎
DOCUMENT_CONFIRMED 条件靠字符串匹配，客户说「上次发过」也会命中
跟进靠轮询扫描，客户量大时需要改成延迟队列
长对话没有记忆分层（见数据表文档第 10 节第 9 条）
未做压力测试，未做多用户并发验证
```

### 8. Next 3 Days

```text
一、连续消息聚合（Message.turnId + Redis 滑动窗口）
    最影响真实体验：客户连发三条不该触发三次 AI
二、把租户规则升级成带条件的规则引擎 + 覆盖率测试
    现在加规则要碰代码，生产环境应该纯配置
三、渠道接入层 + 可观测性
    微信 / 企微 webhook 进来，同时把 AgentRun 的 status 分布
    做成看板 —— 现在要看失败率只能手写 SQL
```

| # | 问题 | 怎么写 |

| 1 | 用了哪些 AI Coding 工具 | 如实列（Codex / Claude Code / Cursor / Copilot…） |
| 2 | AI 主要帮你完成了什么 | 建议写：设计文档的结构化梳理、schema 与类型定义、护栏与测试的初稿、部署配置。**不要说「AI 写完了代码」** |
| 3 | 有没有 AI 方案被你否决或修改 | **必须有具体例子**，见下 |
| 4 | AI 有没有写错代码 / 给错建议 | **必须有具体例子**，见下 |
| 5 | 你怎么验证 AI 生成的代码 | 三个层次：单元测试、真跑验收清单、人工读关键路径 |
| 6 | 本次新增 AI / API 成本 | DeepSeek 大概是几元到几十元量级，写个真实数字 |

### 第 3 题的素材（本次设计过程中真实发生过的）

```text
例子一：AI 建议把 CustomerState 存进编排框架的 checkpoint
        否决理由：状态必须能被业务代码用 SQL 查询、被 UI 展示、
        被销售手工修正，不能藏在框架内部。
例子二：AI 最初把报价护栏写成判断租户 slug 的硬编码分支
        改为数据驱动：规则上挂 enforcement: { kind, condition }，
        两个租户走同一段代码，加租户不用改代码。
例子三：AI 建议为提取客户事实单独调用一次 LLM
        否决理由：每轮变成两次调用，延迟和成本都翻倍。
        改为搭车在同一次结构化输出里返回 facts 增量。
```

### 第 4 题的素材

**要写一个真实发现的错误**，而不是「AI 没犯错」。例如：

```text
AI 生成的取历史消息代码用了 orderBy asc + take 20，
导致模型看到的是最早的 20 条而不是最新的。
发现方式：在会话页连续发 25 条消息后，
发现 AI 完全没提到最新那条内容。
修复：改成 orderBy desc 取完再 reverse。
```

**注意**：题目第二十节要求，如果向真人请教过具体技术问题，要在这里说明。

## 4. 技术答辩速查（题目第二十九节）

| 问题 | 回答锚点 |
|---|---|
| 为什么这个技术栈？ | 单人 24H，**部署复杂度是最大成本**。Next.js 同仓交付前后端、Prisma 让 schema 即文档、Postgres 本地线上一致、常驻容器部署一键可复现 |
| 为什么不用 Python + LangGraph？ | 见第 5 节的分层回答 |
| 为什么数据库这样设计？ | 从题目名词出发，按「写入者 / 频率 / 模式」四步推表；`Message` 是 append-only 事实源，`CustomerState` 是唯一可变状态，`AgentRun` 是为可解释性主动加的黑匣子 |
| Customer State 为什么单独成表？ | 三重身份（AI 输入 / UI 数据源 / 人工可编辑对象），且读写频率与生命周期和 Customer 不同 |
| Customer State 为什么这样设计字段？ | 它是状态机不是缓存。`needHuman` 是棘轮（AI 无权撤销，销售手动解除）；`version` 用于变更审计；两个时间戳让「最后一条是谁发的」不用 join |
| Prompt 如何组织？ | 三段式：角色与目标、企业规则（约束）、输出契约。规则进 system 是为了全局生效。跟进复用同一 pipeline，靠 `trigger` 切换其中一段 |
| Tenant Rule 怎么进 Pipeline？ | 双层保障：prompt 软约束 + `guardrails.ts` 硬校验。护栏是数据驱动的——两个租户用同一种 `enforcement` 但条件不同，加租户不用改代码 |
| 跟进和「客户没回复」是一回事吗？ | **不是。** 最后一条是 SALES 发的才叫需要跟进；最后一条是客户发的，那是我们欠客户一个回复，属于 SLA 违规，应该走催办而不是生成跟进话术 |
| 系统最脆弱的地方？ | ① LLM 输出质量与延迟不可控（已 fallback 兜底）② 并发写同一客户状态（靠幂等约束和 CAS，未做分布式锁）③ 规则硬校验还是关键字匹配，不是规则引擎 |
| 业务量涨 100 倍？ | `AgentRun` 分区归档；`Tenant.config` 拆表；跟进改延迟队列；上京东云 RDS + 只读副本；热点路径加 Redis 缓存；AI 调用异步化 |
| 哪部分代码你最满意？ | `guardrails.ts` —— 把「AI 判断」收敛成可测试的确定性业务规则，让系统真正可解释 |
| 哪部分代码最希望重写？ | `analyze.ts` 的编排耦合了太多步骤，应该改成 pipe 式的步骤数组，方便加步骤和观测 |
| 哪些是你主动没做的？ | `决策记录.md` 第 4 节的八条放弃清单 |
| AI 帮你做了什么 / 做错过什么？ | 见本文档第 3 节 |

## 5. 技术选型类追问（三个版本的回答）

**如果只能讲 30 秒：**

> LLM 在这道题里是系统的一个组件，不是系统的全部。85% 的工作量在数据、状态、租户隔离和交付上，这些用一门 TS 能端到端覆盖；换成 Python 就要变成两个语言、两套类型、两个部署目标，而上线是硬性要求，我要把它压到最低风险。

**如果被追问「LangGraph 不是很适合有状态的流程吗」：**

> 概念上确实对得上。但 LangGraph 的 checkpointer 持久化的是**流程执行状态**，而这道题需要的是**业务实体状态**——它必须能被业务代码直接用 SQL 查询、被 UI 展示、被租户隔离约束、被销售手工修正。所以我的分层是：业务状态放自己的 Postgres，编排用一个可解释的线性 async 函数。如果后续要做多智能体循环或 RAG，我会把编排层换成 LangGraph，但 `CustomerState` 表不会动。

**如果被追问「那 LangChain 呢」：**

> 收益是省几十行胶水代码，代价是 prompt 被中间层包装、调试不透明、依赖变重、API 不稳定。而这道题的评分点之一是「能解释 AI 为什么这么判断」——我要求「发给模型的原文」是一等公民，它被记录在 `AgentRun` 里可以回放，加一层框架正好破坏这个能力。

**如果被追问「如果团队就是 Python 栈」：**

> 那我会改成 Next.js 前端 + FastAPI/LangGraph 的独立 AI 服务，契约就是 `POST /analyze` 收上下文、返回结构化 JSON。业务库仍然是唯一的 Postgres，业务状态仍然在我的表里。多一个部署目标和一次网络跳转是明确代价，团队栈一致性的收益可以覆盖它。

**一句话结论：**

> 不要问哪个技术栈更先进，要问哪个技术栈让「24H 内交付一条可解释的完整链路」这件事的失败风险最小。

## 6. 现场实战预演（题目第三十节）

面试官会给一个新需求或模拟一个线上问题，你需要基于**已提交的代码**分析。这几道几乎必然出现，提前把答案写进代码结构里：

| 现场题 | 你要立刻指出的位置 |
|---|---|
| 增加一条新租户销售规则 | `Tenant.config.rules` —— 只改数据即生效，不用改代码。若需要硬校验，在规则上加 `enforcement`，护栏是数据驱动的 |
| 修改 Customer State | `prisma/schema.prisma` → `state.service.ts` 的更新逻辑 → 前端徽标（三处，按顺序指） |
| 消息重复处理 | `Message.clientMsgId` 唯一约束 + AgentRun 的 `(customerId, triggerMessageId)` 唯一约束 |
| AI 重复回复 | `Message.turnId` + AgentRun 唯一约束（设计里已预留） |
| Follow-up 重复 | **跟进没有 `triggerMessageId`，唯一约束拦不住**。防重靠 `followUpCount` 的比较并交换 + 冷却期 |
| 接口突然报错 | 查 `AgentRun.status` 与 `error`；页面上 fallback 保证不崩；`/dev` 页可以主动复现 |
| 阶段被错误推进 | 查 `AgentRun.guardrailIssues`，护栏拦下的迁移会记录原因 |

**提前准备一句话**：所有「重复」类问题，本系统的统一答案是 **幂等键 + 唯一约束 + 状态机终态判断**，而不是靠 if-else 打补丁。

**唯一的例外是 Follow-up**——它没有天然幂等键，靠乐观锁 CAS 兜底。**主动说出这个例外，比假装统一更强。**
