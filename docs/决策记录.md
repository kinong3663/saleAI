## 2. 关键决策的理由（答辩口径）

### Q2 · 为什么 DeepSeek + 降级策略

国内服务器直连不用代理，成本极低。但兼容接口不一定支持 OpenAI 的 strict `json_schema`，所以代码里做**能力探测**：优先 strict，失败降级 `json_object` + Zod 校验 + 一次修复重试。

**这个降级路径顺手就把进阶挑战 3 的异常处理做掉了一半。**

### Q3 · 为什么每租户三条规则

一条规则只能证明「prompt 里多了一句话」；三条（禁止 / 要求 / 偏好）才能证明**规则体系**生效。而 `HIGH_INTENT` 语义 per-tenant 覆盖，是「阶段定义也是租户配置」这个设计点的可见证据。

**演示关键**：机械之家的 R1 带条件（"确认设备 + 保险需求后"），所以要**两轮铺垫**才能触发——这比单轮对照更有说服力，因为它证明的是**规则的触发条件生效了**。

### Q4 · 为什么只做「解除人工」

`needHuman` 是**棘轮语义**（`prev.needHuman || analysis.need_human`），AI 无权撤销。如果没有出口，状态就是死的。所以「解除人工」不是可选功能，是棘轮的**必要补丁**。

而完整的阶段手改属于"可以但要花时间"，不值得在 24H 内做。

### Q7 · 为什么「最后一条必须是 SALES 发的」

> **「客户没回我」和「我还没回客户」是两件完全不同的事。**

如果最后一条是客户发的，那不是需要跟进，那是**我们欠客户一个回复**——属于 SLA 违规，应该走催办 / 告警，而不是生成一句「亲，考虑得怎么样啦」。

把这两者混为一谈，是把业务语义搞错了。**这是这道进阶题最能拉开差距的判断。**

### Q6 · 为什么进程内定时器可行

京东云是**常驻 Docker 容器**，Node 进程一直活着，`setInterval` 会真的持续触发。而 Vercel 这类 serverless 平台上，代码不是常驻的，`setInterval` 活不过一次请求——**这是「部署决策影响架构自由度」的具体例子**。

### Q12 / Q13 · 为什么跟进复用 pipeline，但不写状态

**复用**：跟进需要的上下文（历史 + 状态 + 租户规则）和主链路几乎一样，重复实现上下文组装、护栏、审计是浪费。

**不写状态**：跟进是我们主动说话，**客户没有提供任何新信息**。如果允许跟进推进阶段，就会出现「我们发了句'考虑得怎么样'，系统把客户判成 HIGH_INTENT」——**这正是状态机失去可信度的典型方式**。

> 原则：**状态迁移必须由客户的新输入驱动。**

## 5. 决策的可逆成本（改哪个便宜，改哪个贵）

写代码时心里有数：**便宜的先做，贵的想清楚再动。**

| 成本 | 决策 | 说明 |
|---|---|---|
| **几乎为零** | `HISTORY_LIMIT` 数值、跟进阈值、超时秒数、模型名、重试次数 | 改常量 / 改环境变量 |
| **低** | 规则文本、prompt 措辞、fallback 话术、`/dev` 工具 | 改字符串 |
| **中** | prompt 分段结构、guardrails 规则集、演示动线 | 要连带改测试 |
| **高** | 表结构、状态迁移规则、Pipeline 分层、租户隔离方式 | 要改 schema + migration + 多处代码 |

**Q12 / Q13 之所以重要，是因为它们属于「中～高」成本那一档**——Pipeline 怎么分层、状态由谁写，一旦写下去再改就要动很多地方。这也是它们在最后一轮才被挖出来的原因。
