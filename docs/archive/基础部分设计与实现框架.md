## 0. 一句话定位

**这不是一个 ChatGPT Wrapper。**

系统真正的主角不是「一次 LLM 调用」，而是 **Customer State 的状态机 + Tenant 规则约束**。
LLM 只负责「理解与建议」，**决定权在代码**：阶段怎么迁移、规则有没有被违反、要不要转人工，都由确定性的代码逻辑兜底。

这条主线决定了后面所有设计：

```text
新消息 → 读旧状态 → 组装上下文(历史+状态+租户规则) → LLM 结构化输出
       → 确定性护栏校验 → 写 AgentRun → 事务更新 CustomerState → 给销售建议
```

面试官最想听的判断是这一句：

> **LLM 提供判断素材，代码持有状态机的最终解释权。**

## 1. 技术选型与理由

| 层 | 选择 | 为什么（答辩口径） |
|---|---|---|
| 前端 + 后端 | **Next.js 14+（App Router）+ TypeScript** | 一个仓库同时交付页面和 API，省掉前后端两套部署，把最危险的一环（上线）压到最低风险；Route Handler 就是后端，将来要拆成独立服务也不用改前端契约 |
| ORM | **Prisma** | schema 就是数据设计文档，migration + seed 一条命令，答辩时能直接对着 schema 讲数据模型 |
| 数据库 | **PostgreSQL**（本地 Docker / 线上 Neon） | 需要 JSON 字段（租户规则、AI 原始输出）和事务；**本地和线上用同一种库**，避免 SQLite → PG 的迁移坑。腾讯云/阿里云 RDS 可无缝替换 |
| LLM | **OpenAI 兼容接口**（小模型，如 `deepseek-chat` / `gpt-4o-mini`） | 走统一 `LLMProvider` 抽象，换模型只改环境变量；用便宜模型 + 上下文裁剪，把成本控制在 ¥200 内 |
| 结构化输出 | **JSON Schema strict 模式 + Zod 双端校验** | 题目明确「建议结构化输出」；schema 既是 prompt 契约，也是运行时校验器 |
| 部署 | **Vercel + Neon**（主）/ **腾讯云轻量 + Docker Compose**（备） | 见 §9，这里有一个必须提前决策的风险点 |

### 明确不选的

- **不上微服务、不上消息队列、不上向量库。** 24H 内引入分布式只会让核心链路跑不通；这些留给 README 的「生产环境演进」。
- **不做精美 UI。** 题目明确点名，漂亮的壳子不加分。
- **不接真实微信。** 用「模拟发送」即可，但**发送结果必须真实落库**。

## 2. 系统架构

```text
┌──────────────────────── 浏览器 ────────────────────────┐
│  Tenant 切换器  │  客户列表  │  会话工作台(三栏)        │
└───────────────────────────┬────────────────────────────┘
                            │ fetch (Route Handler)
┌───────────────────────────▼────────────────────────────┐
│  Next.js Server (Route Handlers)                       │
│   ├─ 所有入口强制 tenantId 作用域（隔离边界）            │
│   └─ Service 层：customer / message / state / tenant    │
├────────────────────────────────────────────────────────┤
│  Agent Pipeline                                        │
│   prompt.ts → llm.ts(timeout/retry) → schema.ts(zod)   │
│   → guardrails.ts(确定性规则) → analyze.ts(编排)        │
├────────────────────────────────────────────────────────┤
│  Prisma → PostgreSQL                                   │
│  Tenant / Customer / Message / CustomerState / AgentRun│
└────────────────────────────────────────────────────────┘
                            │
                     LLM API (OpenAI 兼容)
```

关键点：**只有 `agent/` 目录知道 LLM 的存在。** 其余业务层调用的是 `analyzeCustomerMessage()` 这个普通函数。这样 AI 挂了、超时了、返回垃圾了，都只是这个函数返回不同的结果，不影响 CRUD 主链路。

## 3. 数据模型（本项目的核心产出）

### 3.1 表清单与设计意图

```text
Tenant         一个企业租户 = 一套销售目标 + 规则 + 阶段定义
Customer       客户（必须挂在 Tenant 下）
Message        聊天消息（CUSTOMER / SALES / SYSTEM）
CustomerState  客户当前状态（1:1 Customer，AI 结果的「物化视图」）
AgentRun       每一次 AI 判定的完整审计记录（可回放、可解释）
```

### 3.2 Prisma Schema 草案

```prisma
model Tenant {
  id        String   @id @default(cuid())
  slug      String   @unique          // swimming / machinery
  name      String
  industry  String?
  salesGoal String                    // 自然语言销售目标
  tone      String?                   // 沟通语气
  // 结构化配置：rules[] / stageDefs{} / needHumanTriggers[] / products[]
  config    Json
  createdAt DateTime @default(now())

  customers Customer[]
  messages  Message[]
  runs      AgentRun[]
}

model Customer {
  id         String   @id @default(cuid())
  tenantId   String
  name       String
  channel    String   @default("manual")   // 预留 wechat 等
  externalId String?                        // 渠道侧 ID
  tags       String   @default("")          // 逗号分隔，避免数组类型差异
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  tenant   Tenant         @relation(fields: [tenantId], references: [id])
  messages Message[]
  state    CustomerState?

  @@unique([tenantId, externalId])          // 渠道去重
  @@index([tenantId, updatedAt])
}

enum MessageRole {
  CUSTOMER
  SALES
  SYSTEM
}

model Message {
  id          String      @id @default(cuid())
  tenantId    String                          // 冗余：隔离查询 + 免 join
  customerId  String
  role        MessageRole
  content     String
  turnId      String?                         // 连续消息聚合用（基础版只写不读）
  source      String      @default("manual")  // manual | ai_suggested | followup
  clientMsgId String?                         // 幂等：前端重发不产生重复消息
  meta        Json?
  createdAt   DateTime    @default(now())

  tenant   Tenant   @relation(fields: [tenantId], references: [id])
  customer Customer @relation(fields: [customerId], references: [id])

  @@unique([customerId, clientMsgId])
  @@index([tenantId, customerId, createdAt])
}

model CustomerState {
  customerId            String   @id
  tenantId              String
  leadStage             String   @default("NEW")
  intent                String?                       // 最近一次识别的意图
  needHuman             Boolean  @default(false)
  humanReason           String?
  followUpCount         Int      @default(0)           // 进阶 Follow-up 用
  lastFollowUpAt        DateTime?
  lastCustomerMessageAt DateTime?
  lastSalesMessageAt    DateTime?
  lastAnalysisAt        DateTime?
  version               Int      @default(0)           // 变更审计（乐观锁）
  updatedAt             DateTime @updatedAt

  @@index([tenantId, leadStage])
}

model AgentRun {
  id               String   @id @default(cuid())
  tenantId         String
  customerId       String
  triggerMessageId String?
  status           String                  // SUCCESS | REPAIRED | FALLBACK | FAILED
  model            String
  latencyMs        Int
  attempt          Int      @default(1)
  inputDigest      Json                    // 喂给模型的上下文快照
  rawOutput        String?                 // 模型原始返回，排障利器
  output           Json?                   // 校验后的结构化结果
  rulesHit         String   @default("")   // 命中的租户规则编号，如 "R1,R3"
  error            String?
  createdAt        DateTime @default(now())

  @@unique([customerId, triggerMessageId])  // 幂等：同一条消息只判定一次
  @@index([tenantId, customerId, createdAt])
}
```

### 3.3 三个必须能讲清楚的设计决策

**① 为什么 `Message` 上冗余 `tenantId`？**
租户隔离的最高频查询是「某租户某客户的消息」。冗余后每次查询都能直接带 `tenantId` 条件，不需要 join 回 `Customer` 才能确定归属。代价是插入时多一个字段，换来的是**每一处读路径都天然带租户边界**——漏写才会出问题，而不是忘记写才出问题。（生产环境再加 Postgres RLS 做第二层兜底。）

**② 为什么 `CustomerState` 单独一张表，而不是塞进 `Customer`？**
状态是**高频写、且由 AI 结果驱动**的，客户档案是低频写；分开后互不干扰。状态表天然是「AI 判断结果的物化视图」，有 `version`、`lastAnalysisAt`，可以回放「状态是怎么一步步变过来的」。Demo 时可以直接对着它讲「Customer State 如何变化」，这本身就是评分点。

**③ 为什么一定要 `AgentRun`？**
这是本方案和其他方案最大的分水岭。有了它你才能回答：

- AI 这次的原始返回是什么？为什么判成 HIGH_INTENT？
- 哪条租户规则命中了？（`rulesHit`）
- 上次是不是走了 fallback？
- 同一条消息会被重复判定吗？（唯一约束，幂等）
- 业务量涨 100 倍怎么办？（这就是你要保留的数据源）

面试官问「系统目前最脆弱的地方在哪」，你可以直接翻开 `AgentRun` 的 `status` 分布回答。

## 4. AI Pipeline（一条客户消息进来发生了什么）

### 4.1 时序

```text
销售在会话工作台发一条 CUSTOMER 消息
  │
  ├─ 1. POST /messages  → 校验 tenant 边界 → 插入 Message(role=CUSTOMER)
  │                      更新 state.lastCustomerMessageAt
  │
  ├─ 2. POST /analyze { triggerMessageId }
  │     └─ 幂等检查：AgentRun 已有该 (customerId, triggerMessageId) → 直接返回旧结果
  │
  ├─ 3. 组装上下文
  │      ├─ Tenant.salesGoal + Tenant.config.rules[]
  │      ├─ CustomerState（旧状态：这就是「读取旧状态」）
  │      └─ 最近 N 条消息（默认 20 条，超出部分截断/摘要）
  │
  ├─ 4. Prompt 拼装（§4.3）
  │
  ├─ 5. LLM 调用：JSON strict + 超时(20s) + 重试(1次) + 修格式(1次)
  │
  ├─ 6. Zod 校验 → 失败则 fallback（保底模板 + need_human=true + status=FALLBACK）
  │
  ├─ 7. 确定性护栏 guardrails（§4.4）→ 可能改写 stage/reply/next_action
  │
  ├─ 8. 事务：写 AgentRun + 更新 CustomerState（version+1）
  │
  └─ 9. 返回建议卡片给前端（含 rulesHit，用于证明租户规则生效）
```

### 4.2 结构化输出契约

```ts
// src/server/agent/schema.ts
export const AgentOutput = z.object({
  customer_intent: z.enum([
    '了解产品', '询价', '预约', '犹豫', '投诉', '购买', '其他',
  ]),
  lead_stage: z.enum(['NEW', 'DISCOVERY', 'INTERESTED', 'HIGH_INTENT', 'WON', 'LOST']),
  next_action: z.enum([
    '继续探需', '回答问题', '推进体验', '确认需求', '索取资料', '转人工', '暂不处理',
  ]),
  reply: z.string().min(1).max(500),
  reason: z.string().min(1),
  need_human: z.boolean(),
  rules_hit: z.array(z.string()).default([]),        // 额外加：命中的规则编号
  confidence: z.number().min(0).max(1).default(0.5), // 额外加：置信度
})
```

比题目要求多两个字段，是刻意的：

- `rules_hit`：把「租户规则确实影响了 AI」变成**可视化证据**，而不是嘴上说。
- `confidence`：低置信度 + 高价值动作（报价、成交）时降级转人工，是很自然的兜底策略。

### 4.3 Prompt 三段式组织

**System（固定骨架 + 租户变量）：**

```text
你是「{tenant.name}」的资深销售助理，任务是推动成交。

## 一、企业销售目标
{tenant.salesGoal}          // 例：推动客户预约线下体验课

## 二、企业销售规则（最高优先级，必须遵守）
{rules.map(r => `${r.id}. [${r.type}] ${r.text}`)}
// 例：R1. [禁止] 客户未表达明确兴趣前，不得主动报价
//     R2. [要求] 客户表达「贵 / 考虑一下」时，先给价值锚点，不降价
//     R3. [偏好] 优先引导到店体验，而不是线上答疑

## 三、客户阶段定义
NEW: 首次接触，尚未表达需求
DISCOVERY: 正在了解，需求不明确
INTERESTED: 已表达具体兴趣（问价格/时间/产品细节）
HIGH_INTENT: 明确购买或预约意向，只差临门一脚
WON / LOST: 终态

## 四、输出契约
只输出 JSON，不要任何解释文字。字段与类型严格如下：{...}
reason 中必须说明命中的规则编号（如「命中 R1」）。
```

**User（动态）：**

```text
## 客户当前状态
{ lead_stage, intent, need_human, last_contact_at }

## 最近对话（时间正序）
CUSTOMER: 你们游泳课怎么收费？
SALES: ...
CUSTOMER: 我孩子 4 岁，可以吗？   （← 本次新消息）
```

**租户规则放 system 而不是 user**：它是「约束」而不是「数据」，同时便于命中 prompt 缓存；不同租户 → system prompt 不同 → 判断不同，这就是核心任务 5 的证明方式。

### 4.4 确定性护栏 guardrails（本方案的技术亮点）

LLM 输出**不是最终结果**，必须过一遍纯函数校验。这部分是**最值得写单元测试的地方**（见 §8）。

```ts
function applyGuardrails(out: AgentOutput, ctx: AgentContext): GuardrailResult {
  const issues: string[] = []

  // 1. 阶段单调性：默认不允许回退
  if (stageRank(out.lead_stage) < stageRank(ctx.state.leadStage)) {
    out.lead_stage = ctx.state.leadStage
    issues.push('stage_regression_blocked')
  }

  // 2. 终态保护：WON / LOST 不再被 AI 随意改回
  if (isTerminal(ctx.state.leadStage) && out.lead_stage !== ctx.state.leadStage) {
    out.lead_stage = ctx.state.leadStage
    issues.push('terminal_stage_locked')
  }

  // 3. 租户规则硬校验：乐蒙「未表达兴趣不报价」
  if (ctx.tenant.rules.some(r => r.id === 'R1' && r.type === 'PROHIBIT')
      && !ctx.hasExpressedInterest
      && containsPrice(out.reply)) {
    issues.push('rule_R1_violation')
    out.rules_hit = [...new Set([...out.rules_hit, 'R1'])]
    // 策略：带约束回退重生成一次；仍失败则用去价格模板
  }

  // 4. 转人工一致性：need_human=true 必须配套「转人工」
  if (out.need_human) {
    out.next_action = '转人工'
    out.reply = out.reply || '这个问题我需要请同事帮你确认，稍等片刻～'
  }

  // 5. 低置信度 + 高风险动作 → 降级转人工
  if (out.confidence < 0.4 && ['HIGH_INTENT', 'WON'].includes(out.lead_stage)) {
    out.need_human = true
    out.next_action = '转人工'
    issues.push('low_confidence_escalation')
  }

  return { output: out, issues }
}
```

**答辩口径**：为什么不让 LLM 自己判断阶段迁移？因为阶段是**业务资产**，它决定了后续所有销售动作和报表口径。LLM 有随机性，业务状态机不能有随机性。所以 LLM 只提「建议阶段」，代码校验后才提交。

## 5. Tenant Config：如何证明「规则真的影响了 AI」

### 5.1 配置结构（存 `Tenant.config` JSON）

```jsonc
{
  "rules": [
    { "id": "R1", "type": "PROHIBIT", "text": "客户未表达明确兴趣前，不主动报价" },
    { "id": "R2", "type": "REQUIRE",  "text": "客户犹豫时，先给价值锚点或案例，不降价" },
    { "id": "R3", "type": "PREFER",   "text": "优先推动线下体验预约" }
  ],
  "stageDefs": { "NEW": "…", "INTERESTED": "…" },   // 允许租户覆盖默认阶段语义
  "needHumanTriggers": ["投诉", "要求真人", "涉及退款", "AI 无法确认答案"],
  "products": [{ "name": "亲子游泳体验课", "price": 198 }],
  "replyTone": "亲切、简短、口语化，不超过 80 字",
  "maxFollowUps": 2
}
```

### 5.2 两个种子租户（差异必须明显）

| | 乐蒙亲子游泳 | 机械之家 |
|---|---|---|
| salesGoal | 推动客户预约线下体验课 | 获取客户车辆资料以便技师报价 |
| 核心规则 | 未表达兴趣前**不报价** | 确认设备+保险需求后，**优先索取行驶证** |
| 阶段重点 | HIGH_INTENT = 已约体验时间 | HIGH_INTENT = 已同意提供行驶证 |
| 预期观测差异 | 客户问「多少钱」时，AI 不报价，改引导到店 | 客户问「多少钱」时，AI 主动索取行驶证照片 |

**同一个客户问题 + 两个租户 = 两种回复**，这就是核心任务 5 的验收演示。建议在 Demo 里用同一个客户名在两个租户下各建一份，左右对比。

### 5.3 规则进 Pipeline 的完整路径（答辩必问）

```text
Tenant.config.rules
   ↓ 序列化进 System Prompt 第二节（约束）
   ↓ LLM 被要求把命中规则写进 rules_hit
   ↓ Zod 校验 rules_hit 合法性
   ↓ guardrails.ts 用同一条规则做确定性硬校验（防 LLM 嘴上说遵守实际违反）
   ↓ 落库 AgentRun.rulesHit
   ↓ 前端建议卡片展示「命中规则 R1」，可点击跳转规则详情
```

**双重保障**：prompt 级（软约束）+ 代码级（硬约束）。只做前者的话，LLM 一句「我遵守了」就能骗过去。

## 6. API 与页面设计

### 6.1 Route Handlers

| Method | Path | 说明 |
|---|---|---|
| GET | `/api/tenants` | 租户列表（顶部切换器） |
| GET/PATCH | `/api/tenants/:id` | 租户配置读取 / 演示时现场改规则 |
| GET | `/api/customers?tenantId=` | **必须带 tenantId** |
| POST | `/api/customers` | 创建客户 |
| GET | `/api/customers/:id?tenantId=` | 客户详情 + State + 消息分页 |
| POST | `/api/customers/:id/messages` | 写消息（CUSTOMER / SALES 通用），支持 `clientMsgId` 幂等 |
| POST | `/api/customers/:id/analyze` | 触发 AI 判定，返回建议卡片；幂等 |
| POST | `/api/customers/:id/reply` | 销售确认发送：落库 SALES 消息 + 记录是否采纳/修改了 AI 建议 |
| GET | `/api/customers/:id/runs` | AgentRun 历史（排障 + Demo 讲审计） |

**约定：所有 handler 第一行解析 `tenantId`，所有 service 函数签名以 `tenantId` 开头。** 比如 `getCustomer(tenantId, customerId)` 而不是 `getCustomer(customerId)`——让「忘记隔离」在类型层面变得很别扭。

## 7. 相对进阶能力的预留接口（不做也留钩子）

### 7.1 Follow-up（进阶 1）

不建调度系统，只做**幂等 + 抑制规则**的纯函数，加一个「模拟时间前进」的开发按钮：

```ts
function shouldFollowUp(state, tenant, now) {
  if (isTerminal(state.leadStage)) return false                 // WON / LOST 不跟进
  if (state.needHuman) return false                             // 已转人工，交给人
  if (state.followUpCount >= tenant.maxFollowUps) return false  // 限次数，默认 2
  const idle = now - (state.lastSalesMessageAt ?? state.lastCustomerMessageAt)
  return idle > tenant.followUpAfterHours
}
```

要点：**什么情况下不跟进**比「什么情况下跟进」更重要，这正是题目想看的。表里已经预留 `followUpCount` / `lastFollowUpAt`。

### 7.2 连续消息（进阶 2）

基础版：**先不做**，但 `Message.turnId` 字段已预留。设计说明（写进 README）：

> 生产方案：客户消息进入后不立即触发 AI，而是写入一个短 TTL 的「回合缓冲」（Redis key `turn:{customerId}`，5s 滑动窗口）。窗口内新消息只累积、不调用；静默到期后合并为一次 `turnId` 并触发一次 AI 判定。用 `turnId` 做唯一约束保证一轮只回一次，配 TTL 兜底防止消息永久挂起。

基础版可以做一个**便宜的近似**：前端在客户消息提交后延迟 3s 再调 `/analyze`，期间再发消息则取消上一次定时器。够演示，不引入新基建。

### 7.3 AI 异常处理（进阶 3）

`llm.ts` 统一封装，四类失败对应四种处理：

| 失败 | 处理 |
|---|---|
| Timeout / 网络错误 | 重试 1 次（指数退避），仍失败 → fallback |
| API Error（429/5xx） | 同上，记录 `AgentRun.error` |
| 非法 JSON | 抽取 `{...}` 片段修复一次；仍失败 → fallback |
| 字段缺失 / 类型错 | Zod 校验失败 → 同上 |

**Fallback 输出**（保证系统永不崩溃，题目最低要求）：

```json
{
  "customer_intent": "其他",
  "lead_stage": "<保持原状态不变>",
  "next_action": "转人工",
  "reply": "收到，我先帮你确认一下，马上回复你～",
  "reason": "AI 服务暂时不可用，已降级为人工处理",
  "need_human": true
}
```

原则：**AI 失败 ≠ 数据损坏 ≠ 页面报错。** 状态不前进，落一条 `status=FALLBACK` 的 AgentRun，页面提示「AI 暂不可用，已转人工」。

### 7.4 Tenant Isolation（进阶 4）

已内建：所有读路径带 `tenantId`（本来就这么设计）。生产方案：Postgres RLS + 应用层 session 变量，README 说明即可。

## 8. 测试策略（进阶 5，只测最值得测的）

按「出错代价 × 逻辑确定性」排序，**只测纯函数和边界**：

| 优先级 | 测什么 | 为什么 |
|---|---|---|
| P0 | `guardrails.ts` 全部规则 | 纯函数、无依赖、直接决定业务正确性；这里错了整个状态机会错 |
| P0 | `AgentOutput` Zod schema 解析（含脏数据） | 结构化输出是核心任务 2 的硬要求 |
| P1 | Tenant Isolation：`getCustomer(A, B的id)` 必须查不到 | 隔离边界靠约定，必须有测试兜底 |
| P1 | Fallback 路径：mock LLM 抛错 → 状态不变 + AgentRun=FALLBACK | 验证「AI 挂了系统不崩」 |
| P2 | 阶段单调性 / 终态保护 | 业务资产保护 |

**不测**：UI、CRUD 的 happy path（肉眼看一遍更快）、LLM 输出的语义质量（不可靠且高成本）。

## 9. 部署方案（必须提前决策的风险点）

### 这是本项目最大的单点风险

题目硬性要求「可浏览器访问的线上版本」。而部署平台的可达性取决于**面试官在哪里访问**：

- **Vercel / Render / Railway**：部署最快、HTTPS 免费，但**中国大陆网络直连不稳定**（可能需要代理）。
- **腾讯云 / 阿里云轻量服务器**：国内访问稳定，但要自己配 Docker + Nginx + HTTPS。

### 建议：双部署，主动消除风险

```text
主：Vercel + Neon PG      → 30 分钟内可上线，先拿到一个能点开的 URL
备：腾讯云 2C2G + Docker  → 同一份代码，docker compose up，IP:3000 直接访问
提交时两个 URL 都给出，注明哪个是主站
```

代码层面为双部署做的准备（成本极低，建议一开始就做）：

1. 提供 `Dockerfile` + `docker-compose.yml`（app + postgres），本地就按这个跑，部署时零改造成本。
2. LLM 调用设置 `maxDuration = 60`（Vercel 函数时限），并在服务端做 20s 超时——**不要让请求挂在函数超时上**。
3. Neon 连接串加 `?pgbouncer=true&connection_limit=1`（serverless 场景连接池必须处理）。
4. 数据库迁移用 `prisma migrate deploy` 放进启动脚本，保证两边 schema 一致。

### 环境变量与安全底线（题目 §22 硬要求）

```text
DATABASE_URL=
LLM_API_KEY=          # 只放服务端，绝不加 NEXT_PUBLIC_ 前缀
LLM_BASE_URL=
LLM_MODEL=
APP_PASSWORD=         # 如需简单登录
```

`.env` 进 `.gitignore`，只提交 `.env.example`。**不要用 `NEXT_PUBLIC_` 前缀的任何 key 变量**——这是最容易被抓的低级错误。

## 13. 技术答辩速查（题目 §29 高频问题）

| 问题 | 回答锚点 |
|---|---|
| 为什么这个技术栈？ | 单人 24H，**部署复杂度是最大成本**。Next.js 同仓交付前后端、Prisma 让 schema 即文档、Postgres 本地线上一致、Vercel 分钟级上线 |
| 为什么数据库这样设计？ | `Message.tenantId` 冗余换隔离安全性；`CustomerState` 与 `Customer` 分离因为读写频率与生命周期不同；`AgentRun` 独立因为要审计和回放 AI 决策 |
| Customer State 为什么这样设计？ | 它是状态机而不是缓存。`version` 支持变更审计，`need_human` 是流程岔路，`followUpCount` 为跟进限流预留 |
| Prompt 如何组织？ | 三段式：角色/目标、企业规则（约束）、输出契约；历史消息作为 user 数据。规则进 system 是为让约束全局生效且便于缓存 |
| Tenant Rule 怎么进 Pipeline？ | prompt 软约束 + `guardrails.ts` 硬校验双重保障，命中结果落 `AgentRun.rulesHit` 并在 UI 展示 |
| 系统最脆弱的地方？ | ① LLM 输出质量与延迟不可控（已用 fallback 兜底）② 连续消息与并发写同一客户状态（当前靠幂等约束和事务，未做分布式锁） |
| 业务量涨 100 倍？ | 消息表按 tenantId + 时间分区；AI 调用异步化（队列 + 状态机）；AgentRun 冷数据归档；加 Redis 做回合缓冲与去重 |
| 最满意的代码？ | `guardrails.ts`——把「AI 判断」收敛成可测试的确定性业务规则，让系统真正可解释 |
| 最想重写？ | `analyze.ts` 的编排耦合了太多步骤，应改为 pipe 式的步骤数组，便于加步骤与观测 |
| AI 帮你做了什么 / 做错过什么？ | 见 `AI_CODING_NOTES.md`（提前准备一个真实例子） |
