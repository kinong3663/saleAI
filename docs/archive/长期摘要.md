先纠正一个可能的误解：**原文永远不删。** 我前面说的"用档案代替历史"指的是**进 prompt 的东西**变了，不是数据库里的东西变了。`Message` 表是事实来源和审计记录，一条都不能丢。变的只是"每轮往上下文里塞什么"。

## 三层记忆结构

把"记忆"拆开，你会发现它其实是三件不同的事，用三种不同的结构存：

```
L1 档案层   长期 · 结构化 · 事实        不随对话增长   → 持久化注入
L2 摘要层   中期 · 有损 · 叙事          缓慢增长       → 持久化注入
L3 原文层   短期 · 精确 · 不可篡改       固定窗口       → 最近 N 条注入
```

**L1 是档案**：孩子 4 岁、住浦东、在意安全、问过两次价格。它解决"跨轮记住关键信息"，成本恒定。

**L2 是摘要**：事实抓不住趋势。"客户一开始说预算无所谓，聊了三轮开始反复问折扣"——这不是某一条事实，是一段过程。销售的判断很依赖这种趋势。做法是滑出窗口的一批消息归档时压成一段摘要，追加到 L2。

**L3 是最近原文**：话术质量依赖精确措辞。"客户刚才说'有点贵'"和"客户嫌贵"对生成回复的影响完全不同。所以原文不能全砍，只是窗口缩小。

三层加起来大概 1600 token，**和对话长度无关**。而 500 条对话的原文是 25000–50000 token。这才是这个设计的真正价值：**成本从"随历史线性增长"变成"恒定"。**

## 你的核心问题：是的，提取必须靠 AI，但不要新开一次调用

如果为了提取事实单独调一次模型，每轮就变成两次调用——延迟翻倍、成本翻倍。正确做法是**搭车在同一次输出里**：

```ts
export const AgentOutput = z.object({
  // ...原有字段
  facts_add: z.array(z.object({
    key: z.string(),
    value: z.string(),
    evidence: z.string(),      // ← 必须是客户原话的引用
  })).default([]),
  facts_correct: z.array(z.object({
    key: z.string(),
    old_value: z.string(),
    new_value: z.string(),
    evidence: z.string(),
  })).default([]),
})
```

多数轮次这两个数组是空的（客户没说新信息），**所以它的边际成本接近于零**。只有真的出现新信息时才有产出。

## 关键防线：存证据，不存结论

这是我认为整个设计里最重要的一条。

Agent 记忆系统最典型的失败模式是**幻觉固化**：模型某一轮猜测"客户可能预算在 2 万以内"，写进数据库，下一轮被当作已知事实注入，模型基于它推理，再产生新的推断……**几轮之后，数据库里全是模型自己编的东西，而且它现在有了"事实"的地位。**

解决办法不是调 prompt 让它别瞎猜，而是**让幻觉在结构上可检出**：

> **每条事实必须附带 `evidence`，而且代码会校验这段引用必须是该客户某条真实消息的子串。校验不通过，整条事实丢弃。**

```ts
function validateFact(fact, messages) {
  const found = messages.some(m => m.content.includes(fact.evidence))
  return found ? { ok: true } : { ok: false, reason: 'evidence_not_grounded' }
}
```

这个检查很便宜（一次字符串匹配），但它把"模型编的"和"客户说的"在入库前就分开了。**没有原话支撑的推断，根本进不了系统。**

再补一条：`key` 用**受控词表**，不是自由文本。否则你会看到 `child_age` / `孩子年龄` / `kids_age` 三个 key 描述同一件事。词表由租户配置定义——乐蒙关心 `child_age`，机械之家关心 `vehicle_model` / `license_plate_available`。**这又是租户规则进系统的一个自然落点。**

## 数据模型

```prisma
model CustomerFact {
  id              String   @id @default(cuid())
  tenantId        String
  customerId      String
  category        String   // IDENTITY | NEED | CONSTRAINT | OBJECTION
  key             String   // 受控词表：child_age / budget / concern / location
  value           String
  evidence        String   // 客户原话
  sourceMessageId String   // 可追溯到具体消息
  confidence      Float    @default(0.8)
  status          String   @default("ACTIVE")   // ACTIVE | SUPERSEDED | REJECTED
  validFrom       DateTime @default(now())
  expiresAt       DateTime?

  @@index([tenantId, customerId, key])
}
```

为什么是表而不是 `CustomerState` 上的一个 JSON 列？三个理由：

**能查。** "所有家里有 3–6 岁孩子的客户"是一条 SQL，不是全表扫 JSON。

**能改单条。** 客户要求删除某项信息（合规要求）时，一条 `DELETE` 比 read-modify-write 一个 JSON 稳定得多。

**能溯源。** 每条事实指向具体消息。销售在 UI 上看到"孩子 4 岁"，可以点一下看到客户原话，判断对不对。

## 事实会变，所以用"失效"而不是"覆盖"

客户上个月说"孩子 3 岁"，这个月说"快 4 岁了"。直接覆盖会丢掉两件事：他什么时候说的，以及旧值是什么。

写成 `supersede`：

```ts
// 同 key 出现新值时
await tx.customerFact.updateMany({
  where: { customerId, key, status: 'ACTIVE' },
  data: { status: 'SUPERSEDED' },
})
await tx.customerFact.create({ data: { ...newFact, status: 'ACTIVE' } })
```

只有 `status = 'ACTIVE'` 的进 prompt。历史留在库里——这和你之前问的状态迁移是同一个思路：**不覆盖，留版本。**

## 注入侧要写得非常明确

```text
## 已知客户信息（已核实，均有客户原话支撑）
- 孩子年龄：4 岁        （客户说：我孩子 4 岁）
- 关注点：怕水/安全      （客户说：会不会呛水）
- 已询问价格，尚未报价   （客户说：你们多少钱）

## 约束
「已知客户信息」之外的内容一律视为未知。
不要根据客户称呼、语气、头像等信息推测其年龄、职业、收入或家庭情况。
信息不足时，通过提问获取，不要假设。
```

最后那句约束不是形式主义。**模型很擅长从一句话里"顺带推断"出一堆东西，而这些推断一旦入库就在后面每一轮被当作事实用。**

## 必须警惕的几个失败模式

**幻觉固化** — 上面用 evidence 校验挡住了。

**过度推断** — 明确禁止推断人口统计属性和敏感属性。这不只是准确率问题：把模型猜测的健康、宗教、家庭状况当成客户档案存起来，在多数司法辖区都是高风险数据处理。**只存客户明确说过的，不存模型推导的。**

**错误传播** — 万一一条错事实进了库，它会影响后面每一轮。所以 UI 上必须让销售能删、能改这些事实，并且改动要回写到 `status='REJECTED'`（顺便成为模型的负样本，下次可以提醒它这类推断不可靠）。

**陈旧** — "下个月想去游泳"有有效期。所以留了 `expiresAt`。

## 24H 里做到哪一步

我的排序是：**先保证核心链路跑通、能上线**，档案系统排在后面。

如果还有余量，只做最小版本：`CustomerState` 加一个 `facts` JSON 列 + `AgentOutput` 加 `facts_add` + evidence 子串校验 + UI 上展示。不做查询、不做 supersede、不做词表。大概一个多小时。

但它是一个很好的**进阶挑战 6** 候选——因为这道题明说了"如果你认为有其他功能更值得做，说明为什么把时间投入在这里"。而"长对话下如何保持上下文有效"恰恰是这道题从"能跑"走向"真有价值"的分水岭。README 里写清完整的三层设计和 evidence 校验机制，本身就能说明你对 agent memory 的理解深度。

回到你最初的问题：**是**,提取要靠 AI 完成，它每轮搭车输出"新增事实"，代码校验后入库。但记住主线——**模型提出，代码裁决**。事实能不能入库，不由模型说了算，由"能不能在原文里找到那句话"说了算。
