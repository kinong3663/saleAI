## 0. 结论先行

> **LLM 在这道题里是系统的一个组件，不是系统的全部。**
>
> 这道题真正的工作量在「数据 + 状态 + 隔离 + 交付」上，而不在「编排」上。
> Next.js + TS 能用**一门语言**端到端覆盖这些；Python 方案会把它变成**两个语言、两套构建、两个部署目标**。
> LangGraph 解决的「多步 + 有环 + 需要检查点」问题，在这道题里的链路是**线性的**；而真正需要被持久化的业务状态（CustomerState），必须落在**自己的 Postgres 里**，因为它要能被 SQL 查询、被 UI 展示、被租户隔离约束。

## 1. 先定义判据

选型不该问「哪个更先进」，该问「哪条路径的失败风险最小」。我用五个判据：

| 判据 | 说明 |
|---|---|
| **① 工作量覆盖度** | 技术栈覆盖了题目的百分之多少工作量？剩下多少要用第二种语言兜？ |
| **② 交付风险** | 上线是硬性要求。这条路径上有几个必须做对的环节？ |
| **③ 契约一致性** | AI 结构化输出的字段，从数据库到 UI 要经过几处类型定义？会不会漂移？ |
| **④ 可解释性** | 题目要求「能解释 AI 为什么这么判断」。技术栈会让这件事更清楚还是更模糊？ |
| **⑤ 脚手架成本** | 在 24H 里，框架本身要吃掉多少时间？ |

**关键判据是 ① 和 ②。** 因为 24H 是硬约束，任何「两套栈」的方案都会在这个约束下暴露风险。

## 2. 这道题的实际工程量分布

把六个核心任务按技术栈归属拆开：

| 任务 | 主要落在哪一层 | Python 生态更优？ |
|---|---|---|
| 1. 客户与聊天记录（CRUD + 持久化） | Web 后端 + DB | 否，打平 |
| 2. 客户列表 / 详情 / 聊天界面 | 前端 | 否，毫无优势 |
| 3. AI 结构化判断 | LLM 调用（**一次**） | 略优（生态厚） |
| 4. Customer State 读写 + 状态展示 | Web 后端 + 前端 + DB | 否，打平 |
| 5. 销售编辑 / 发送 / 落库 | 前端 + 后端 | 否，毫无优势 |
| 6. Tenant 配置 + 规则注入 | 数据 + Prompt | 略优（规则结构用 Pydantic 更顺手） |
| 7. 上线部署 | 部署 | 否，**Python 明显更麻烦** |

真实的 AI 编排代码（prompt 拼装 + 调 LLM + 校验 + 更新状态）大概 **150–250 行**。

而 CRUD、API 路由、页面、状态管理、租户隔离、部署配置加起来 **2000 行以上**。

> **AI 编排约占 15%，其余 85% 都是标准 Web 工程。**

选型要为 85% 服务，而不是为最「性感」的那 15% 服务。

### 还有一个被忽略的证据

题目第二十三节明确列出「**24H 内不建议花大量时间做**」的清单，其中包括：

```text
模型训练
SFT / LoRA
大型 Dashboard
```

而 Python 生态**最有优势的恰恰是模型训练、数据处理、RAG 与实验**这类场景。

> **题目排除掉的，正是 Python 最强的部分；题目要求交付的，正是 Web 栈的主场。**

同时题目第十八节写着：「我们不会因为使用某种框架加分。更关注为什么这样选择，以及最终有没有成功交付。」

也就是说，选型的得分点在**论证质量 + 交付结果**，不在框架的先进程度。

## 3. 逐维度对比

| 维度 | Next.js + TS + Prisma | Python + FastAPI + LangGraph |
|---|---|---|
| 语言数量 | **1** | 2（Python + JS），或前端退化到模板引擎 |
| 部署目标 | **1 个**（Vercel 一键 / 单容器） | 2 个（前端静态托管 + 后端服务），或自建 Docker + Nginx + HTTPS |
| 跨域 / 鉴权 | 同源，无 CORS | 跨域 CORS + Cookie 域 + 环境变量双份 |
| 结构化输出契约 | **Prisma 类型 → Zod → 前端 props，一份类型** | Pydantic Model + TS interface **两份**，需手工同步 |
| 类型安全边界 | 端到端 | 前后端之间是 HTTP JSON，类型在边界断裂 |
| AI 编排 | 15% 的代码，可用 60 行 async 函数表达 | 生态更厚，但本题只需一次调用 |
| 后台任务（跟进调度） | Vercel Cron / pg-boss / 外部 cron 打点 | Celery / APScheduler 更成熟 ✅ |
| 长任务（>60s） | Serverless 有函数时限，需拆分或降级 | 常驻进程无限制 ✅ |
| LangGraph 成熟度 | LangGraph.js 存在，但 Python 版是参考实现 ✅ | Python 版更成熟 |
| 冷启动 | Vercel 函数冷启动，需控制依赖体积 | 常驻进程，无冷启动 ✅ |
| 24H 内脚手架成本 | 低（create-next-app 起步） | 中（两套工程 + 双部署） |
| 答辩可解释性 | prompt 与 JSON 全链路可见 | 框架中间层会遮蔽「实际发了什么给模型」 |

Python 一方真正领先的项目，我用 ✅ 标出来了——**不该假装它们不存在**。

但请看它们属于哪一类：**长任务、后台调度、LangGraph 成熟度**。这三项在基础部分（Part A）里**一个都用不上**，只在进阶挑战 1（Follow-up）里部分相关。

而代价（两个部署目标、两套类型、跨域与鉴权）在**第一天就会付**。

## 4. 为什么不选 LangChain

先讲公道话：LangChain 不是不能用，而是**它省的胶水代码（几十行）小于它带来的不确定性和不透明**。

具体有五个问题：

**① 抽象泄漏。** `LLMChain` / `AgentExecutor` 这类抽象在设计时假设了「通用」，但当你需要精确控制 prompt 的每一段、精确控制重试条件、精确控制解析失败时的回退时，它反而变成阻碍——你要读它的源码才能知道它到底拼了什么。

**② 版本迭代快，API 不稳定。** Python 版 LangChain 的破坏性变更非常频繁。24H 的时间盒里踩到一次 breaking change，损失的是不可恢复的时间。**这不是技术优劣问题，是风险管理问题。**

**③ 调试不透明，直接伤害本题的得分点。** 题目要求展示 `reason`、解释 AI 为什么这样判断。而 LangChain 默认会往 prompt 里注入你没意识到的 system 文本、few-shot 示例、格式指令。当模型输出不符合预期时，**你无法确定到底是你的 prompt 的问题，还是框架包装的问题**。

在本项目里，我要求「给模型发了什么」是一等公民——所以它被记录在 `AgentRun.inputDigest` 里，可以直接回放。**加一层框架正好破坏这个能力。**

**④ Token 成本不可控。** 框架注入的内容会进 token 计费。题目有 ¥200 成本约束，虽然不苛刻，但「不知道钱花在哪」本身就是坏味道。

**⑤ 依赖体积与冷启动。** LangChain 会拖进几十个传递依赖，部署到 Serverless 会显著变慢冷启动。

### 直接对比：结构化输出这件事

用 Vercel AI SDK + Zod：

```ts
const { object } = await generateObject({
  model: openai('gpt-4o-mini'),
  schema: AgentOutput,        // Zod schema 自动转 JSON Schema
  system: systemPrompt,
  prompt: userPrompt,
})
// object 已经是类型安全的 AgentOutput
```

自己写（不依赖任何框架）也就 30 行：调 SDK → 解析 JSON → Zod 校验 → 失败重试。**这 30 行是可以完全解释、完全测试的代码**，而 LangChain 的等价能力需要你去理解它的 OutputParser 体系。

## 5. LangGraph 的单独评估（这个更值得认真回答）

LangGraph 和 LangChain 不是一回事，必须分开评价。

### 5.1 承认：它确实对应得上

LangGraph 的核心概念和本项目的结构**有真实的重合**：

| LangGraph 概念 | 本项目对应物 |
|---|---|
| State（图状态） | CustomerState |
| Node（节点） | 组装上下文 / LLM 调用 / 校验 / 更新状态 |
| Reducer（状态归并） | 状态更新逻辑 |
| Checkpointer（检查点） | CustomerState 的历史版本 |
| `interrupt`（人工中断） | `need_human = true` 转人工 |

所以「用 LangGraph 做这道题」**不是荒谬的**，它是一个 legit 的设计选项。如果面试官提出这个方案，你不该直接说「太重了」，那是外行话。

### 5.2 但有一个根本问题：检查点 ≠ 业务状态

这是最关键的一点，也是最有区分度的回答：

> **LangGraph 的 checkpointer 是「流程执行状态」的持久化，它存在框架自己的 store 里（SqliteSaver / PostgresSaver）。
> 而这道题需要的是「业务实体状态」——它必须能被业务代码直接用 SQL 查询。**

具体来说，如果状态只活在 LangGraph 的 checkpoint 里，以下能力全部丢失或变得别扭：

```text
✗ 一条 SQL 查出「当前租户所有 HIGH_INTENT 的客户」→ 客户列表页排序/筛选
✗ 租户隔离的显式边界（checkpoint 表里没有 tenantId 语义）
✗ 销售在 UI 上直接修正状态（这是核心任务 4 的一部分）
✗ 状态与 Message 的事务一致性（同一次写操作里更新两者）
✗ 状态变更的审计与 version 递增
✗ 现场实战题「修改 Customer State」——你得先讲清楚框架怎么存
```

而题目核心任务 3 的全部意义就是：

> **Customer State 是这个产品的一等业务实体，不是某个编排引擎的内部变量。**

正确的分层应该是：

```text
业务状态（CustomerState）      →  自己的 Postgres，业务代码直接读写
流程编排（编排/重试/中断）      →  可以用 LangGraph，也可以用一个 async 函数
```

**LangGraph 可以替换掉我那个 60 行的 `analyze.ts`，但它绝不能替换掉 `CustomerState` 表。**

### 5.3 本项目的编排复杂度实测

本项目的 Pipeline 是：

```text
组装 → LLM → 校验 → 护栏 → 落库 → 更新状态
```

**一条直线，最多加一次重试分支。**

LangGraph 的价值曲线是：步骤数越多、环越多、需要中断恢复的场景越复杂，收益越大。

| | 步骤数 | 有环？ | 需要中断恢复？ | LangGraph 收益 |
|---|---|---|---|---|
| 本题基础链路 | 6 | 否 | 仅 need_human 标记 | 低 |
| 本题 + Follow-up 调度 | 8 | 否 | 是 | 中 |
| 生产级多轮 Agent（工具调用 + 反思循环） | 20+ | **是** | 是 | **高** |

用一个为「多步有环图」设计的引擎去跑一条直线，收益是负数：

```text
收益：代码更"标准"
成本：多一个重依赖 + 图定义的心智负担 + 部署时多一层版本约束 + 答辩时多一个问题解释不清
```

### 5.4 还有一个细节差异

LangGraph.js 存在，但 **Python 版是参考实现**，文档、示例、社区答案都围绕 Python。

这意味着：如果坚持用 LangGraph，**在 24H 内遇到问题时，你的搜索命中率在 Python 一侧更高**。

这是 Python 方案最实在的一个优势，我不回避它。（应对方法见 §7。）

## 6. 什么情况下我会推翻上面的结论

这是我认为最能体现判断力的部分——**一个选型结论必须给出它的证伪条件**，否则就只是偏好。

如果题目变成下面任意一种，我会立刻改用 Python + LangGraph：

| 条件 | 为什么结论反转 |
|---|---|
| 要做**多智能体循环**（探需 Agent ↔ 报价 Agent ↔ 审核 Agent 互相修正） | 这就是 LangGraph 的主场 |
| 要做 **RAG**：检索历史成交案例、产品知识库来生成话术 | Python 的向量库 / 检索生态明显更厚 |
| 要做**离线评测 / 微调 / 数据分析** | 题目明确排除，但若包含则 Python 无争议 |
| 需要**长时间运行的后台任务**（多轮跟进序列、定时批处理） | 常驻进程 + Celery 比 Serverless + Cron 自然 |
| **面试方/团队栈本身就是 Python** | 交付要贴合对方环境，这本身就是最强的选型理由 |

反过来，本题的实际情况是：

> **这是「在业务系统里嵌一次 LLM 调用」，不是「围绕 LLM 构建一个 Agent 系统」。**

前一类的正确形态是 **Web-native 栈**；后一类才是 **Python 编排栈**。

判断依据很简单：**看 LLM 调用是「系统的一个函数」，还是「系统的核心循环」。** 本题是前者。

## 7. 如果一定要用 Python：混合架构方案

不该把结论说成「非此即彼」。真实工程里有第三条路：

```text
┌──────────────────────────┐         ┌────────────────────────────┐
│ Next.js（Web + 业务 API） │  HTTP   │ Python 服务                 │
│ · 页面 / CRUD / 租户隔离  │ ──────► │ · FastAPI + LangGraph       │
│ · CustomerState 读写      │         │ · 只做 AI 编排              │
│ · Postgres（唯一业务库）  │         │ · 状态仍通过 API 回写业务库  │
└──────────────────────────┘         └────────────────────────────┘
```

契约就一个：`POST /analyze` 收 `{history, state, tenantRules}`，返回 `AgentOutput`。

**这样做的代价必须说清楚**：

- 多一个部署目标（Vercel + 一台 VPS 或 Railway）
- 多一个网络跳转 → 延迟增加、失败模式增加（Python 服务挂了怎么办？→ 走 fallback）
- 多一份 schema 定义（Pydantic ↔ Zod）需要同步

在 24H 内，**这个代价换来的收益（更优雅的编排写法）不足以覆盖风险**。所以我在基础部分不这么做。

但在 README 里我会写明：**如果团队栈是 Python，这就是推荐的落地形态**，并且现在的 `LLMProvider` 抽象已经为它预留了接口。

## 8. 现在的实现如何为将来迁移留口子

选型不是一次性决定，要给未来留门。当前设计已经具备三个可迁移点：

**① 编排入口唯一。**
所有 AI 逻辑只暴露 `analyzeCustomerMessage(tenantId, customerId, triggerMessageId)` 一个函数。要换成 LangGraph，只需要换掉这个函数的内部实现，调用方（Route Handler、测试）一行不用改。

**② 步骤可拆。**
`analyze.ts` 里每一步都是纯函数（`buildContext` / `buildPrompt` / `callLLM` / `validate` / `applyGuardrails` / `persist`），本身就是「节点」的天然候选。要改成图，就是把它们接起来。

**③ 业务状态与编排解耦。**
`CustomerState` 是独立的业务表，编排层只通过 `stateService` 读写它。**这意味着编排引擎是可插拔的，而业务资产是不可替换的**——这正是分层正确的标志。

> 迁移路径：`analyze.ts` 的线性编排 → LangGraph 图；`CustomerState` 表**保持不动**。

## 9. 答辩口径（浓缩版）

如果只能讲 30 秒：

> **LLM 在这道题里是系统的一个组件，不是系统的全部。90% 的工作量在数据、状态、租户隔离和交付上，这些用一门 TS 能端到端覆盖；换成 Python 就要变成两个语言、两套类型、两个部署目标，而上线是这道题的硬性要求，我要把它压到最低风险。**

如果被追问「LangGraph 不是很适合这种有状态的流程吗」：

> **概念上确实对得上，但 LangGraph 的 checkpointer 持久化的是流程执行状态，而这道题需要的是业务实体状态——它必须能被业务代码直接用 SQL 查询、被 UI 展示、被租户隔离约束、被销售手工修正。所以我的分层是：业务状态放自己的 Postgres，编排用一个可解释的线性 async 函数。如果后续要做多智能体循环或 RAG，我会把编排层换成 LangGraph，但 CustomerState 表不会动。**

如果被追问「那 LangChain 呢」：

> **LangChain 在本题的收益是省几十行胶水代码，代价是 prompt 被中间层包装、调试不透明、依赖变重、API 不稳定。而这道题的评分点之一是「能解释 AI 为什么这么判断」——我要求「发给模型的原文」是一等公民，它被记录在 AgentRun 里可以回放，加一层框架正好破坏这个能力。**

如果被追问「如果团队就是 Python 栈」：

> **那我会改成 Next.js 前端 + FastAPI/LangGraph 的独立 AI 服务，契约就是 POST /analyze 收上下文、返回结构化 JSON。业务库仍然是唯一的 Postgres，业务状态仍然在我的表里。多一个部署目标和一次网络跳转是明确代价，团队栈一致性的收益可以覆盖它。**

---

## 10. 一句话总结

> **不要问哪个技术栈更先进，要问哪个技术栈让「24H 内交付一条可解释的完整链路」这件事的失败风险最小。**
>
> 这道题的答案是：**Web-native 栈做骨架，LLM 作为其中一个可插拔的组件，业务状态永远握在自己的数据库里。**
